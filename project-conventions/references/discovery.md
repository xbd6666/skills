# 证据发现

## 发现边界

优先使用用户明确提供的仓库或模块路径。仓库根可以由版本控制根、工作区配置、解决方案或工作区清单推断；无法唯一确定且会改变输出时，保留为未决事项。

默认只做无副作用读取：文件清单、文本搜索、文件内容、版本控制状态与差异、构建清单和配置键检查。验证权限见 [request-contract.md](request-contract.md)。

大型仓库先做有界清单，再读取代表性文件。默认排除明显噪声和生成目录，例如：

- `.git`、`.svn`、`.hg`；
- `node_modules`、`vendor`、包缓存；
- `bin`、`obj`、`dist`、`build`、`coverage`；
- 生成客户端、编译输出、模型产物、大型数据集；
- 已由清单或配置明确标记的生成目录。

如果生成目录本身就是约定对象，只读取证明其角色所需的最小内容，并在覆盖范围中说明例外。

## 按任务范围发现

单点检查适用于核对一条路径、链接、命令来源或某项局部规则。先确认目标范围及适用指令，再读取目标内容和直接相关证据；用户已经明确的范围、布局、报告语言和目标文档语言直接沿用。无需为此盘点无关模块、公共契约、持久化或部署表面。

发现跨模块影响、权威冲突、继承变更或直接证据不足时，扩展到相关文档、依赖和反例；按 [inheritance.md](inheritance.md) 检查必要关联关系，不自动扩大为全仓库调查。

建立约定体系、进行全范围审查、评估整体布局或进行范围较广的规则维护时，执行完整发现：

1. 列出顶层目录、项目或工作区清单、入口文件和测试目录。
2. 先枚举目标范围内全部层级的 `CONVENTIONS.md`、`AGENTS.md` 及用户点名的约定文档，再补齐仓库根到目标范围的祖先文档和必要的权威来源。目标为仓库根时仍须枚举其后代，不以根到目标的读取链代替子级清单；明确排除的区域单独列出。
3. 读取与当前范围直接相关的 `README.md`、`CONTRIBUTING.md`、`ARCHITECTURE.md`、`.editorconfig`、`CODEOWNERS`、构建文件、包清单和配置结构，识别已有主题权威及读取优先级，不仅凭文件名判断。
4. 识别语言、框架、入口、公共契约、依赖方向、持久化、生成物、部署表面和稳定验证命令。
5. 约定文档清单区分已读取、仅发现和无法读取；业务实现可抽样。完整审查结论须覆盖范围内已发现的适用约定及其必要关联关系；文档过多或读取受阻时，报告已覆盖部分和剩余清单，不宣称全范围无冲突。

读取配置时优先记录文件路径、配置键和行为，不复制配置值。发现疑似密钥、令牌、连接字符串、个人信息或生产地址时立即脱敏。

## 证据分类

每条候选规则先分类，再决定是否进入约定：

| 类型 | 含义 | 可否直接形成规则 |
| --- | --- | --- |
| 用户明确决定 | 当前请求中已经确认的范围、边界或偏好 | 可以 |
| 既有权威规则 | 适用的约定、贡献指南、架构文档或强制政策 | 可以，但需检查是否与实现冲突 |
| 工具强制事实 | 编译、包清单、静态配置或生成机制实际强制的行为 | 可以描述为事实约束 |
| 重复惯例 | 多个代表性实现一致遵循的模式 | 只能作为候选规则，标明证据强度 |
| 例外或冲突 | 与主模式或文档不一致的实现 | 不得被自动提升为规则 |
| 假设 | 证据不足的推断 | 不得写成既定规则 |

仓库“碰巧这样写”不等于团队“要求这样写”。对重复惯例至少记录代表性路径、反例和置信度。只有一个样本时，不把它描述为稳定惯例。

## 规则确认与候选采纳

证据类型说明规则来自哪里，结论状态说明能否作为生效条款写入：

| 结论状态 | 判定条件 | 输出方式 |
| --- | --- | --- |
| 已确认 | 用户明确决定了具体规则及范围；或适用的既有权威规则、工具强制事实已核实且没有未决冲突 | 可以在获准写入的范围内形成生效条款；工具事实只描述实际强制的约束 |
| 候选 | 重复惯例等证据支持拟议规则，但尚未获得明确采纳 | 留在报告或文档的待确认区，标明不生效，不混入正式规则 |
| 冲突或未决 | 证据相互矛盾、适用范围不明或缺少确认依据 | 记录证据、分歧和确认点，不形成新的生效条款 |

候选转为“已确认”需要用户明确采纳可唯一识别的规则内容及适用范围；可一次确认方案中列明的候选采纳清单。记录确认依据，保留原始证据类型，不把用户采纳后的规则伪装成工具强制事实。一般写入授权、更多相同样本或更高置信度都不自动完成采纳；已明确采纳的内容无需重复确认。

用户直接要求生成文档时，可以先写入已确认规则，将未采纳候选列为不生效的待确认事项。候选或冲突影响其他规则时，按 [请求契约的暂停与部分交付](request-contract.md#暂停与部分交付) 处理关联变更组；不为记录候选修改受保留的文档，相关待确认事项留在交付报告中。

## 路径状态与未来要求

路径状态与规则是否已确认分别判断：

- **现存路径**：核对实际位置、职责和引用；将本轮获准创建的约定文档作为交付目标，并在写入后验证其存在。
- **已批准但尚未启用的未来路径**：用户已确认具体路径、用途和适用范围时，可写为未来要求，注明实际创建状态及启用条件，保留确认依据。尚未创建的路径使用代码形式，不伪装成现状目录树或可访问链接；已创建但未满足启用条件的要求仍不作为现行规则。规则确认不授权创建业务目录、代码或配置。
- **示意路径**：明确仅用于举例，不作为实际文件、权威来源或已采纳的未来要求。

尚未采纳的未来布局仍是候选。未来路径和示意路径不能充当本轮读取链、父约定或权威依据的现存来源；新约定文档之间的必要引用须在同一获准变更组交付后有效。

## 文档与实现漂移

现有文档和代码不一致时，记录为以下之一：

- 文档声明、实现违反，责任未定；
- 实现已普遍迁移、文档可能过时，责任未定；
- 多种实现并存，尚无统一规则；
- 用户已明确裁决。

未获得用户裁决前，不通过修改文档或选择其中一方来掩盖冲突。

## 既有内容复核与处置

检查或更新已有约定时，同时复核本轮范围内的旧内容；单点任务只处理点名条款及必要关联内容，不借清理扩展到无关章节或模块。结论状态回答规则能否生效，内容处置回答现有文字如何维护，两者分别判断。不能只新增规则而跳过范围内已发现的过时内容，也不要求每次修改都进行全仓清理。

| 内容情况 | 判定与建议处置 |
| --- | --- |
| 仍有效的规则、职责和执行入口 | 保留；必要时简化表述，保持适用范围、条件、强度和例外 |
| 过时的事实、路径、标识符、命令或职责映射 | 核实重命名、迁移或替代关系后更新，同时处理相关目录图、路由和引用 |
| 重复规则、说明或实现细节 | 核对权威、语义及适用范围后合并或改为引用；仅对同范围同语义的内容去重，保留能防止高代价错误的简短提醒 |
| 已被替代或适用对象已退役的条款 | 查明承接规则、退役依据和剩余适用对象；无继续保留理由时建议删除，不因当前代码未遵守或暂未使用就认定规则失效 |
| 通用口号、历史过程、一次性任务记录或过密的现状快照 | 判断是否影响当前决策；无执行价值的内容可删减，有长期价值的背景可建议迁往其专业文档，必要理由、示例、例外和风险边界仍保留 |
| 模板编写指令、占位内容或清理后无用的空章节 | 移除；不要将这类指令改写成仓库的长期规则 |
| 依据不足、语义有冲突或作用范围不明 | 保留原文并列为待确认，不用删减掩盖分歧 |

“搜索不到”不足以证明内容已退役。先核对搜索范围、实际读取状态、重命名或迁移、生成机制、已批准未来要求和示意用途；无法读取或尚未检查的来源不视为不存在。引用存在也不证明其内容、用途和适用范围仍正确。父规则和覆盖项的承接关系按 [inheritance.md](inheritance.md) 处理。

### 中间状态的收尾

- **待确认事项**：已采纳的内容进入相应生效条款，移除同一事项的旧候选或未决表述；已明确否决、取消或解决的事项不继续留作待确认。未获裁决的内容不能因存放时间长而自动删除。
- **未来要求**：相关路径及全部启用条件已满足时，转为现状或当前规则，去掉过期的“尚未创建”表述；仅目录出现不代表已启用。取消或被替代须有明确依据，未启用但仍获批准的要求继续保留。
- **临时限制或例外**：核实其原定期限、退出条件及当前事实，退出后恢复应适用的常规要求；没有明确结束条件或无法确认其已满足时，不自行宣布到期。一次性任务记录与持续有效的执行护栏分别判断。
- **历史证据**：旧运行结果不能充当当前验证结论。保留有用的验证入口及必要前提；清理理由、历史过程和本轮验证记录放在交付报告中，需迁入既有专业文档时仍受文件与权威迁移范围约束，不默认新建归档文件。

### 处置记录与执行

沿用三种工作方式：检查报告给出处置建议；方案列明拟实施的处置及待裁决部分；获准更新时按 [request-contract.md](request-contract.md) 执行。不改变有效要求的整理与实质规则变更分开说明，已覆盖的授权不重复询问。

对拟变更或待确认的内容记录：原位置、保留／更新／合并／迁移／删除／待确认、依据、对有效规则及关联文档的影响；合并或迁移还须说明承接位置。使用[方案模板的处置表](../assets/制定约定方案.template.md#既有内容处置)，检查报告可用对应建议表或简短文字，无需给每条未变规则制作台账。

联动处置按关联变更组完成，写入后按 [verification.md](verification.md) 对照有效规则和引用。已准确、简洁且没有新证据的内容保持稳定，不为体现清理而改写或按字数比例删减，也不把清理记录重新堆进正式约定。

## 项目形态

项目形态允许多标签，不要求单选。常见证据及关注点：

| 证据 | 可能形态 | 主要关注 |
| --- | --- | --- |
| 前端框架清单、页面、组件、路由 | 前端应用 | 路由、状态、API 客户端、样式、可访问性、视觉验证 |
| 服务入口、端点、控制器、中间件、OpenAPI | 后端或 API | 契约、鉴权、验证、服务边界、配置、可观测性 |
| 明确的领域、应用、基础设施或适配器目录 | 分层架构 | 依赖方向、层职责、端口与适配器、持久化边界 |
| 多个应用、包或工作区清单 | Monorepo | 所有权、共享代码、跨包依赖、构建与发布边界 |
| 公共导出、包清单且无应用入口 | 库或包 | 公共 API、兼容性、示例、版本和依赖策略 |
| 命令、参数解析、终端入口 | CLI 或工具 | 参数、标准输出、错误输出、退出码、幂等性 |
| 数据、特征、流水线、模型或 notebook | 数据或 ML | 来源、阶段、实验、产物、复现、隐私 |
| 基础设施清单、容器、编排或工作流 | 基础设施 | 环境、状态、密钥、发布安全、生成文件 |
| 移动平台工程或跨端框架 | 移动应用 | 页面、导航、平台目录、权限、资源和发布配置 |
| 内容、站点生成器或文档配置 | 文档站点 | 内容结构、元数据、资源、发布和链接验证 |

使用具体清单、入口和目录组合判断，不使用 `app`、`api`、`src` 等单个通用名称直接定型。混合仓库应记录多个形态及各自证据。

## 布局决策

- **仅根目录**：小型、单一用途或共享规则足以覆盖的仓库。
- **根目录加模块**：多个应用、包、层或高风险模块拥有不同职责和契约。
- **仅模块**：用户只针对某个子目录，且不希望建立仓库级政策。

模块文档只在职责独立、公共契约不同、错误代价高或局部规则确实不同的地方创建。不要为每个文件夹机械生成一对文档。

仅模块布局不要求先有根级 `CONVENTIONS.md`。已核实没有父约定时按继承说明声明“无”，保留其他实际适用的指令与权威来源，不为补齐模板扩大创建范围。

## 发现记录格式

完整方案或多规则维护使用[方案模板中的证据表](../assets/制定约定方案.template.md#证据与结论)。证据来源须可复核，类型与结论状态按本文件判定；规则影响说明写入、引用、排除或待确认，并标明置信度。

把观察事实与建议规则分开，避免在同一个句子中把推断写成事实。
