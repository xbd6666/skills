# 阶段六：执行开发计划

本阶段由产品开发工作流的入口选择。它在已有工作区修改授权内执行阶段五计划，或实施目标、边界和验收明确且无需独立计划的任务；它产出经过任务级自检和适用评审的变更，但在阶段七完成前不得宣称整体完成。

跨阶段的确认、实施授权、验证授权及评审触发条件见[入口的“公共契约”](../SKILL.md#公共契约)；本文件只定义阶段六特有的执行循环、偏差处理和任务交接。

## 目标

按上游需求、适用的 Spec 和计划实施恰好需要的变更，持续暴露阻塞和偏差，并让每项任务留下可复查的实施与验证记录。执行效率不能覆盖业务决策、授权边界或质量门槛。

## 输入与分流

开始前确认：

- 有可执行计划，或者已经满足入口[“直接进入阶段六”](../SKILL.md#直接进入阶段六)门槛并说明为何不需要独立计划；
- 已读取适用项目规范和任务涉及的最小上下文；
- 采用的需求、Spec、计划修订及依据有效性已按入口的[“产物修订与下游有效性”](../SKILL.md#产物修订与下游有效性)核对，受影响的旧状态不能直接沿用；
- 工作区修改和计划内本地验证满足入口的[“阶段六实施授权”](../SKILL.md#阶段六实施授权)与[“验证动作与授权”](../SKILL.md#验证动作与授权)；
- 仓库历史、远程系统及真实数据操作是否授权分别明确。

如果无法复查覆盖当前文件、动作和验证的授权，停止并按入口规则请求；取得授权后，在首次写入前说明当前阶段、授权依据和覆盖范围。若计划、Spec 或业务目标存在上游错误，按入口的回退分型和本阶段“偏差与阻塞处理”确定去向。

## 实施前基线与并行修改

- 首次写入前记录当前检出状态、相关文件已有的已暂存与未暂存差异，以及目标未跟踪文件的现有内容；非 Git 工作区记录相关文件内容或可复查快照。基线应足以重建本次修改前的相关状态，优先复用宿主或任务记录，不要求清理工作区、全库快照或新增账本文件。
- 标明哪些改动原已存在，不把它们归于本次任务；在授权范围内叠加修改并保留用户已有内容，不为得到干净差异而覆盖、撤销或暂存用户改动。
- 每次编辑目标前核对它与最近一次读取或自身写入后的预期状态。发现外部改动时重新读取并判断合并影响；无法安全合并或影响授权范围时，停止受影响操作并说明冲突。最初基线保留用于归因，不因重读而把用户新增改动算成本次结果。
- 实施后的归因结合基线、实际编辑记录与并行变化，分别说明本次修改、用户已有或新增修改和生成物。无法确定来源的差异明确标为未能归因，不宣称是本次产生或擅自清除。

## 执行模式

选择与复杂度和宿主能力相称的模式：

| 模式 | 适用情况 | 执行方式 |
| --- | --- | --- |
| 直接执行 | 已按入口门槛直接进入阶段六，或通过微小变更快捷通道的任务 | 当前代理实施、自检，再按入口规则衔接阶段七 |
| 分批执行 | 任务相关、需要共享上下文或检查点 | 按依赖顺序执行一批，检查后继续 |
| 独立任务执行 | 多个边界清晰、可独立评审的任务 | 可由独立代理逐任务实施；控制者维护计划和授权边界 |

不要并行修改重叠文件、同一迁移链或共享可变状态。是否使用独立代理不改变任务要求，也不授权额外仓库或外部操作。

## 任务状态

维护可恢复的任务记录，至少区分：`待开始`、`进行中`、`阻塞`、`已实施待评审`、`已评审`。记录任务标识、采用的上游修订、结果有效性、实施前基线位置、实际变更、执行的验证、发现的偏差和下一步；宿主已有计划或任务工具时优先复用，不强制创建新的账本文件。结果有效性与任务进度分开，修订后的处理遵循入口规则。

直接实施等路径缺少需求编号时，在任务记录或可复查对话中按入口[“需求追溯标识”](../SKILL.md#需求追溯标识)补齐来源映射，不为此补建需求或计划文件。

## 单任务执行循环

### 1. 准备任务简报

向实施者提供任务目标、完整任务文本、上游标识及采用修订、全局约束、相关上下文、有效的前置任务结果、实施前基线和允许的操作。不要让实施者依赖未提供的会话历史，也不要要求它重新决定业务规则。

### 2. 实施与测试

遵循项目已有测试策略。新行为、缺陷修复和可测试重构通常先建立能失败的行为验证，再编写最小实现并重构；如果任务属于生成物、纯配置、探索性原型，或项目缺少相应测试基础，采用计划中约定的替代证据并说明原因。

不得因为“测试先行”而删除用户已有实现、扩大重构范围或违反项目规范。测试策略存在实质选择且会改变交付结果时，回到上游确认。

### 3. 实施者自检

完成任务后检查：

- 是否实现了任务要求且没有遗漏；
- 是否加入未要求的功能或顺手重构；
- 是否遵循项目结构、命名和错误处理模式；
- 测试是否验证真实行为及适用边界；
- 实际改动是否仍在授权范围内；
- 输出中是否存在警告、失败或未经验证的完成声明。

发现问题先修正并重跑相关验证，再报告结果。

### 4. 任务级评审

根据入口“安全只读与必须确认条件”中的具体影响和宿主能力选择独立或当前代理复核，并分别给出：

1. **规格符合性**：是否少做、误解或多做；
2. **实现质量**：结构、错误处理、测试、可维护性及适用的安全问题。

入口要求独立评审时，在宿主支持的情况下交给独立评审者；其他任务由当前代理做明确的二次复核。实施者自检不能替代要求的独立评审。

评审问题按影响分级。会影响正确性、规格符合性、安全或维护的事项必须修复并重新评审；纯偏好建议只有在范围允许且有实际收益时采纳。评审意见与计划文字冲突时，不要让评审者或实施者自行裁决，回到控制者或用户确认。

### 5. 记录并继续

记录实际变更、验证命令及结果、评审结论和遗留项，再将任务标为已评审。只有前置任务完成后才开始依赖任务。

## 偏差与阻塞处理

- 缺少上下文：补充上下文后重试；
- 任务过大：回到阶段五重新拆分；
- 不影响任务边界、外部行为或验证方式的内部细节：作为实施时决定记录并继续；
- 计划技术决定错误，影响任务边界、依赖或验证方式：回到阶段五修订并重新检查受影响任务；
- Spec 不可实现或有冲突：回到阶段四；
- 业务规则或范围不清：回到阶段三；
- 工具、依赖或环境失败：尝试安全替代验证；仍不能推进时报告证据和阻塞条件；
- 超出授权：停止受影响操作并请求相应授权。

不要用相同输入无限重试，也不要为了继续推进而静默缩小验收范围。

## Git 与外部操作

遵循入口的[“检查点可以合并，决定分别成立”](../SKILL.md#检查点可以合并决定分别成立)。未取得对应授权时，停止相应仓库或外部操作，继续可完成的已授权工作并按交接门槛处理；阶段六计划中的相关步骤不能自行建立仓库或外部状态授权。

## 阶段交接门槛

达到以下任一门槛后，按入口[“阶段六到七自动衔接”](../SKILL.md#阶段六到七自动衔接)进入阶段七，不再请求阶段选择；用户明确要求暂停时按入口例外处理。不把正常交接要求强加给受阻任务：

### 正常交接

- 任务级自检和适用评审已完成，必须修复的问题已复核；
- 实际变更仍符合需求、适用的 Spec、计划和授权范围；
- 已记录验证结果及原始证据位置，由阶段七核对覆盖范围与可复用性后形成整体结论；
- 工作区中无未经解释的额外改动归因于本次任务。

### 阻塞交接

- 列出未完成任务及其实际进度、已有变更和仍未完成的自检、验证或评审，不将它们标为已通过；
- 提供可复查的阻塞证据、已尝试动作及结果，说明继续工作需要的新授权或外部条件；
- 记录相对实施前基线的已有改动、遗留状态和下一步恢复条件；能安全完成的范围检查仍应完成，无法检查的部分明确说明；
- 交给阶段七形成 `阻塞` 报告，不要求先完成被阻塞条件妨碍的自检或评审，也不得声称整体完成。当前仍能在已有授权与条件内处理的任务继续执行，不用阻塞交接提前结束。

## 输出契约

输出已实施任务、实际改动、任务级验证与评审、计划偏差、阻塞和遗留项，以及交给阶段七的验证范围。不要在本阶段使用“全部完成”“已修复”或“所有测试通过”等整体结论。

## 快速检查

- 当前任务是否有明确上游来源、前置条件和授权？
- 实现是否恰好满足任务，没有少做或多做？
- 测试和评审是否与变更影响相称？
- 是否用实施前基线和编辑记录区分了用户改动与本次结果，并检查并行修改？
- 发现计划、Spec 或需求错误时是否回到了正确阶段？
- 是否把局部实施结果误写成整体完成结论？
