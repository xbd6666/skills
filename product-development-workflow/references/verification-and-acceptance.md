# 阶段七：验证与验收

本阶段由产品开发工作流的入口选择，或按入口[“阶段六到七自动衔接”](../SKILL.md#阶段六到七自动衔接)进入。它用当前、完整、可复查的证据判断实施是否满足需求、适用的 Spec、质量要求和验收标准；没有足够证据时必须报告真实状态，不能声称完成。

跨阶段的验证分类、授权继承和评审触发条件见[入口的“公共契约”](../SKILL.md#公共契约)；本文件只定义阶段七特有的验证矩阵、证据判断和交付结论。

## 目标

把“实施者认为已经做好”转为“证据支持哪些结论、哪些仍未证明”，形成可供用户验收的开发交付报告。本阶段不自动提交、合并、推送、发布、部署或修改外部系统。

## 输入与分流

输入至少包含：已确认需求和验收标准、适用 Spec、实施计划或直接实施说明、实际变更与任务状态，以及已有的任务级验证和评审记录。阻塞交接可以提供未完成标记、已有证据及继续所需条件，不要求先补齐成功的自检或评审。

记录本轮采用的上游修订，按入口的[“产物修订与下游有效性”](../SKILL.md#产物修订与下游有效性)核对任务、评审和验证结论。旧修订下的“已评审”或“通过”不自动成为当前修订的证据。

- 任务未实施或必须修复的评审问题仍开放，且当前仍可继续处理：回到阶段六。
- 未完成项已记录可复查的阻塞条件，且需要新授权或外部条件才能继续：留在本阶段形成 `阻塞` 报告，不循环回到阶段六，也不得声称完成。
- 代码揭示计划遗漏：回到阶段五。
- 实现与 Spec 冲突且无法仅靠修复消解：回到阶段四；业务意图不清时继续回退。
- 验证动作不满足入口的授权条件：停止相应验证，说明命令、目标、副作用和范围后请求授权，不用其他证据冒充该结果。

## 验证前授权预检

执行任何验证前，按入口的[“验证动作与授权”](../SKILL.md#验证动作与授权)完成副作用分类和授权检查，本阶段不重复定义授权继承条件。授权不足不等于验证失败；停止未授权动作，将对应验收项标为 `未验证`，或在无法形成可靠结论时标为 `阻塞`。

## 证据先于结论

在声称某项工作完成、修复或通过前：

1. **识别结论**：要证明的是构建成功、测试通过、缺陷修复、需求满足，还是可交付；
2. **确定证据**：列出能直接证明该结论的命令、检查、截图、回读或人工场景；
3. **重新执行**：在当前变更状态下运行完整验证，不依赖旧输出或实施者摘要；
4. **读取结果**：检查完整输出、退出码、失败数量、跳过项和警告；
5. **判断支持度**：证据不支持时报告失败、部分通过或阻塞；只有支持时才作相应结论。

不能运行验证时说明原因、已尝试的替代方法和仍未证明的内容。不要用“应该”“看起来”或局部测试替代完成证据。

## 核心流程

### 1. 建立验证矩阵

把每项需求、适用的 Spec 行为和任务映射到验证证据。没有独立 Spec 时直接从需求追溯到任务：

```text
R-1 → S-1（如适用）→ T-1 → V-1：命令或人工场景 → 结果
```

验证必须覆盖正常路径，以及适用的失败、权限、空值、边界、并发、兼容和迁移场景。无法覆盖的项明确列为未验证，而不是从其他通过项推断。

### 2. 检查变更范围

结合阶段六的[“实施前基线与并行修改”](executing-development-plans.md#实施前基线与并行修改)记录检查当前状态和差异，区分本次修改、用户已有或新增修改和生成文件。独立进入验收而缺少基线时，可用可复查的原始快照、补丁或提交记录补证；仍无法归因的差异标为未知并说明对验收的影响，不凭当前差异反推其来源。确认没有未经授权的范围扩张、调试残留、密钥、临时文件或意外格式化；适用时运行差异空白错误检查。

### 3. 执行分层验证

按项目实际情况选择并记录：

- 与本次变更直接相关的最小测试；
- 构建、类型检查、静态分析、格式或 lint；
- 受影响模块或完整测试套件；
- 接口、UI、文件、数据库迁移或兼容性验证；
- 适用的安全、权限、性能和可访问性检查；
- 需要人工判断的截图、回读、演示或验收场景。

先报告定向验证，再单独报告更广验证。完整套件因依赖、环境或既有问题失败时，区分本次引入失败和可复查的预存失败；没有证据时不要声称失败与本次无关。

### 4. 整体评审

对完整变更做一次整体复核，分别判断：

- **规格符合性**：每项需求是否被实现，是否有遗漏、误解或越范围功能；
- **实现质量**：架构一致性、错误处理、测试质量、维护性和适用的安全风险；
- **交付完整性**：必要文档、配置、迁移、兼容与回滚说明是否齐备。

完整变更命中入口的独立评审条件时，在宿主支持的情况下使用独立评审。发现必须修复的问题后回到阶段六，修复并重新执行受影响验证与评审；不能用首次评审替代复核。

### 5. 对照验收标准

逐项给出 `通过`、`失败`、`未验证` 或 `不适用`，并附证据位置。自动化证据不能替代明确要求的人工体验或业务验收；需要用户操作或判断时，提供最小验收步骤和预期结果。

### 6. 形成交付结论

使用以下状态之一：

| 状态 | 判定 |
| --- | --- |
| 已通过开发验收 | 必需验证和评审通过，无阻塞项；需要的用户人工验收也已完成 |
| 待用户验收 | 自动验证通过，但仍需要用户完成已列明的人工判断 |
| 条件通过 | 核心目标有证据支持，用户明确接受已披露的限制或未验证项 |
| 未通过 | 存在失败、规格不符或必须修复的问题 |
| 阻塞 | 缺少环境、权限、依赖或外部条件，无法形成可靠结论 |

只有第一种状态可以声称开发交付完成。其他状态均不能声称完成，必须同时说明剩余条件和下一步。

## 验证与验收报告

报告至少包含：

1. **结论与范围**：验证的提交或工作区状态、采用的上游修订、交付状态和未包含内容；
2. **需求追溯**：需求、适用的 Spec、任务和验证证据的映射；
3. **执行证据**：命令、退出码、通过/失败/跳过数量，以及截图或回读位置；
4. **评审结果**：规格符合性、代码质量和交付完整性；
5. **失败与遗留项**：本次问题、预存问题、未验证项和影响；
6. **人工验收**：步骤、预期结果、负责人和状态；
7. **授权边界**：是否允许提交、合并、推送、发布、部署或其他外部变更。

## 开发交付边界

阶段七完成表示开发工作已有可复查结论，不自动表示已经合并、发布或在生产环境可用。需要仓库历史操作、远程变更、发布、部署、生产迁移、线上冒烟或监控时，必须使用适用流程并获得单独授权。

## 快速检查

- 每个完成声明是否有当前、直接且完整的证据？
- 每个验证动作是否完成副作用分类，并有覆盖当前命令、目标和范围的授权？
- 是否读取了完整输出、退出码、失败和跳过数量？
- 定向结果、完整套件结果和人工验收是否分开？
- 是否把预存失败、未验证项或环境阻塞如实披露？
- 修复评审问题后是否重新验证和复核？
- 是否把开发完成误当成提交、发布或生产可用授权？
