# 阶段七：验证与验收

以可复查证据判断本轮实际变更是否满足需求、适用契约和验收标准。阶段六正常或阻塞交接均可进入；进入验收本身不扩大权限。

## 输入与行动

核对已确认需求、验收标准、必要 Spec、计划或直接实施说明、实际变更及已有验证和评审。采用修订已改变时先按[产物有效性](artifact-contracts.md#产物修订与下游有效性)判断影响。

可在现有条件及授权内修复的遗漏或必修问题回阶段六处理；计划错误回五，契约错误回四，业务意图不清回三。确实缺少外部条件或新增授权时留在本阶段报告阻塞，不在六和七之间空转。

任何新验证先按[动作与授权](action-boundaries.md#验证副作用)核对。未授权动作标“未验证”；授权不足不是测试失败，也不是通过。

## 既有验证证据的复用

先看证据是否足以支持要作出的结论，再决定是否补跑。既有结果可复用须同时满足：

- 覆盖该验收项及当前采用的需求／契约；范围差异有可复查的无影响依据。
- 能识别验证时的代码及未提交内容；相关测试、配置、依赖、环境或数据没有影响结论的变化。依赖实时状态的结果仍满足时效要求。
- 执行目标、命令或检查方法、完整原始结果、适用的退出码、失败及跳过项均可读取；口头“通过”或摘要不足。

只补齐缺失、变化或无法确认有效的部分；无法界定影响才扩大到模块或完整套件。形成结论前核对相关状态，记录复用依据和本轮新增证据。已通过的相关检查不为“更保险”无依据重复运行。

## 既有评审结论的复用

核对原始记录中的评审者及独立性、覆盖范围、采用依据、被评审内容、问题处理和复核结果；这些必须与本轮最终变更一致，或有可复查的保留依据。按[评审条件](action-boundaries.md#决定与评审)需要独立评审时，自检不能替代。

局部评审只支持其覆盖部分；多份局部通过仍需核对任务配合、整体需求覆盖和交付完整性。已有有效评审覆盖最终完整变更时直接复用，只补缺失或受影响部分。评审不能替代验证或必需人工验收。

## 形成结论所需证据

1. **范围核对**：对照实施前基线和编辑记录区分本次变化、用户已有或新增改动、生成物。基线不全时尝试原始快照或补丁；仍不能归因的差异明确标未知，不擅自清除。
2. **需求追溯**：每项需求对应任务和证据，可用 `R → S（如适用）→ T → V`。没有编号时在本轮记录补齐来源映射，不补造上游文件。
3. **适用验证**：选择与变化相称的行为测试、构建、静态检查、UI／接口回读或人工场景。覆盖实际相关的正常和失败、权限、边界、并发、兼容等要求，不套全量清单。
4. **整体复核**：检查需求是否少做、多做、误解，错误处理和实现质量是否合格，必要文档及交付说明是否齐全。发现必修问题后修复并复核受影响证据。
5. **逐项判定**：每个验收项标“通过／失败／未验证／不适用”，附证据或不适用理由。读完整结果、退出码、失败数和跳过项；定向通过不能代表全套或生产通过。

整体套件失败时，用证据区分本次问题和已存在问题；不能无依据归为环境或历史问题。不能运行检查时说明尝试、替代证据和未证明内容。必需用户体验或业务验收不能被自动化测试取代。

## 交付状态

| 状态 | 判定 |
| --- | --- |
| 已通过开发验收 | 必需验证、适用评审和必需人工验收均通过，无阻断交付的遗留项 |
| 待用户验收 | 技术验证及适用评审通过，仅剩明确的用户人工验收 |
| 条件通过 | 核心目标有证据、没有必修问题；用户明确接受列明限制下的阶段性交接 |
| 未通过 | 已有证据证明验收要求不满足 |
| 阻塞 | 缺环境、授权、依赖或外部条件，无法完成必需实施、验证或评审 |

先完成能做的修复与核查，不用状态标签提前结束。整体阻塞时仍保留已知“失败”和“未验证”；条件通过不能掩盖必修问题、必需评审缺失或核心目标无证据，也不改变验收标准。

只有“已通过开发验收”可称开发交付完成，其余说明剩余条件。结尾按[阶段交接](../SKILL.md#每轮交付与结尾)点名阶段七、交付状态及下一步或停止点。

报告长度随任务调整，保留结论范围、关键需求与证据映射、命令及结果、评审覆盖、未验证项和恢复／人工验收步骤。引用已有完整证据，避免粘贴全部日志。该结论不授权提交、合并、推送、发布、部署或生产验证。
