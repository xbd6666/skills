# 阶段五：编写实施计划

把已确认需求和必要的 Spec 转成实施者能够执行、验证和交接的任务。不重复设计业务规则，不预写大段生产代码。

## 采用依据

核对需求、验收标准、项目规范与必要的已确认 Spec，按[产物与追溯](artifact-contracts.md)记录来源、采用修订及有效性。需求已清楚且无需新技术契约时可以没有独立 Spec；局部明确任务可按入口直接实施条件省略计划。

业务缺口回阶段三，契约未定回阶段四。实际文件位置、构建命令和测试方式先只读调查，不能猜测路径、函数或命令。

## 可执行任务

按依赖和结果拆分，每项任务包含：

| 内容 | 要达到的程度 |
| --- | --- |
| 需求与契约来源 | `R → S（适用时）→ T → V`，没有新增无来源功能 |
| 目标与边界 | 实施者知道要实现什么、不能改变什么 |
| 文件和职责 | 创建／修改／测试位置有依据；尚未定位时给定位方法 |
| 依赖和步骤 | 前置结果、关键输入输出、必要实施顺序 |
| 完成证明 | 有依据的命令或检查、预期结果及适用回退点 |

任务粒度按独立可验证结果决定，不按固定分钟数或行数。内部支撑工作说明服务哪项需求；相关重构只在本次正确实施需要时纳入。

说明全局约束、验证副作用，以及适用的迁移、兼容和运行要求。小改动采用相称验证，不强制为纯文案或低影响可逆改动新写测试；已有有效证据可在验收时核对复用。

默认由当前代理按依赖执行。宿主支持、授权允许且任务边界独立时可以建议委派；重叠文件、迁移链或共享状态不并行修改。不由执行方式推导 Git、worktree 或外部操作权限。

## 保存与实施检查点

内容、状态和路径确定且无影响正文的实质未决项时，直接保存 `implementation-plan.md` 并回读，记录修订、上游依据、任务、验证及未决项。计划自检应覆盖需求遗漏、依赖冲突和验证不足；审阅状态如实标记，不因保存就称已获批准。

计划可执行且当前阶段产物已交付后，读取[动作与授权](action-boundaries.md)，列明拟实施范围、非目标、验收和验证副作用，请求尚缺的阶段六选择与实施授权。可以合并确认计划和实施；已有有效批准则直接沿用。

结尾按[阶段交接](../SKILL.md#每轮交付与结尾)给出阶段五、计划链接与状态、待决事项和下一步。未获实施授权时停在检查点；已获覆盖授权时继续执行，不让用户重复批准。
