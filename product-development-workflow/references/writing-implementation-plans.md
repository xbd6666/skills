# 阶段五：编写实施计划

本阶段由产品开发工作流的入口选择。它把阶段四确认的 Spec，或不需要新增技术契约的阶段三确认需求，转为文件级、可执行、可验证的实施计划；它不重新决定业务规则，不修改生产代码，也不默认创建分支或提交。

## 目标

让缺少当前会话背景的实施者也能按计划完成工作，并能从每项需求追溯到任务和验证证据。计划应具体到职责、文件、依赖和验证，但不要预写大段生产代码或用虚假精度掩盖未知项。

## 输入与分流

开始前至少具备：已确认的需求与验收标识、适用项目规范、用户允许的计划产出方式，以及任务需要时已确认的 Spec。

- 适用的 Spec 仍有会改变用户可见行为、权限、数据、公共接口或验收结论的未决项：回到阶段四；若源头是业务意图不清，回到阶段三。
- 修改局部、可逆，现有项目模式足以指导实施，且独立计划不会降低风险：只有按入口定义的授权检查点取得用户后续肯定回复，并获得覆盖阶段六实施范围的工作区修改授权后，才能直接进入阶段六。
- 计划内容已经足以形成完整正式产物：必须先确定 `implementation-plan.md` 的具体路径并请求文档写入授权；尚未取得授权时停止并请求，不要改为直接输出完整计划。
- 已按入口规则取得对应文档写入授权：必须创建或更新 `implementation-plan.md`；计划确认本身不构成文件写入授权。
- 用户明确要求仅在对话中产出、明确拒绝文档写入、没有可写工作区，或任务明确止于分析或非正式草稿：在对话中输出完整 Markdown 计划，并停在计划产物。

## 信息状态

| 标签 | 含义 |
| --- | --- |
| 上游约束 | 已确认需求、适用的 Spec、非目标和项目规范中必须保持的内容 |
| 已观察事实 | 从仓库、测试、配置或文档读取到的当前状态及来源 |
| 计划技术决定 | 不改变外部语义、为形成可执行任务而确定的技术细节 |
| 实施时决定 | 不影响任务边界或接口，可由实施者按项目规范决定的细节 |
| 待确认 | 不同答案会改变范围、公共行为、数据、权限、兼容或验收的事项 |
| 执行授权 | 用户允许的计划文件写入、工作区修改、仓库操作和外部变更范围 |

## 核心流程

### 1. 定向调查实施面

读取完成计划所需的最小仓库范围：项目规范、相关入口、相邻实现、测试布局、构建配置和已存在的迁移或接口模式。记录事实来源；不要把当前代码自动升级为未来需求。

### 2. 建立追溯关系

沿用上游稳定标识，例如 `R-1`。有 Spec 时为其行为增加 `S-1`，并为任务增加 `T-1`；没有独立 Spec 时可直接从需求追溯到任务。明确例如：

```text
R-1 → S-1（如适用）→ T-1/T-2 → V-1
```

每项上游需求必须至少由一个任务实现，并有可判断的验证方式。任务不能加入没有上游来源的功能；必要的内部支撑工作要说明其服务的任务。

### 3. 设计文件与职责

先列出预计创建、修改和验证的文件或模块，以及各自职责和相互接口。未知位置可以写明定位方法，不得虚构路径、类型或函数签名。

遵循现有项目结构。只有当前结构会阻碍本次正确实施时，才把相关重构列入计划，并说明必须保持的外部行为。

### 4. 拆分可验证任务

一个任务应形成可独立评审的结果，并包含：

- 对应的需求标识，以及有独立 Spec 时对应的 Spec 标识；
- 目标、前置任务和不允许改变的约束；
- 创建、修改和测试位置；
- 输入、输出或相邻任务依赖的接口；
- 实施步骤及适用的测试先行要求；
- 验证命令或人工证据；
- 完成条件和可能的回退点。

不要机械追求固定分钟数。配置、脚手架和文档应归入真正需要它们的交付任务；只有相邻结果可以被独立接受或拒绝时才拆开。

### 5. 安排顺序与执行方式

按依赖关系和风险安排任务。修改同一文件、同一迁移链或共享状态的任务默认串行；只有文件和状态互不冲突时才标记可并行。

根据任务选择执行方式：

- 局部任务：当前代理直接执行；
- 多个紧密相关任务：当前会话分批执行并设置检查点；
- 多个边界清晰的独立任务：在宿主支持且用户未限制时，可建议使用独立子代理执行和评审。

执行方式只是建议，不得由此推导创建 worktree、分支、提交或外部变更的授权。

### 6. 自检并交接

逐项检查 Spec 覆盖、任务依赖、名称与接口一致性、验证充分性以及占位文本。计划发现上游缺口时先回退修正，不要把问题留给实施者猜测。

## 计划最小结构

删除不适用章节，不保留空占位：

```markdown
# [功能名称] 实施计划

> 状态：草稿 / 待审阅 / 可执行
> 上游需求与 Spec：[位置或对话摘要；无独立 Spec 时说明原因]

## 1. 目标、范围与全局约束
## 2. 当前实现与文件职责
## 3. 追溯矩阵
## 4. 任务、依赖与执行顺序
## 5. 验证策略
## 6. 迁移、兼容、回滚与运行约束
## 7. 计划技术决定、实施时决定和未决项
## 8. 执行方式与授权边界
```

## 交接门槛

进入阶段六前确认：

- 每项需求和适用的 Spec 行为都映射到任务与验证方式；
- 任务的输入、输出、依赖和完成条件清楚；
- 适用的失败路径、迁移、兼容、回滚和非功能约束已进入任务；
- 没有会改变外部行为或范围的未决项；
- 计划已完成自检，并按用户要求完成审阅；
- 已通过入口定义的授权检查点和用户后续肯定回复取得覆盖阶段六实施范围的工作区修改授权；仅有计划文档写入授权时不得进入阶段六，分支、提交、推送、部署和其他外部变更仍分别受其授权约束。

## 输出契约

遵循入口的“阶段三至五的持久化产物”规则。计划已保存时，在对话中输出计划摘要、可点击的文档位置、状态、追溯覆盖情况、计划技术决定、仍需的用户决定、推荐执行方式和授权边界，不重复粘贴完整正文；仅在入口规定的对话产出例外成立时，才输出完整 Markdown 计划及相同的交接信息。没有经过覆盖阶段六实施范围的工作区修改授权检查点和用户后续肯定回复时，停止在计划产物，不进入阶段六。

## 快速检查

- 计划是否忠实实现已确认需求和适用的 Spec，而不是重新设计产品？
- 每项任务是否有明确上游来源和验证方式？
- 路径、接口和命令来自调查，还是未经验证的猜测？
- 任务边界是否便于独立实施和评审？
- 是否把计划确认误当成工作区、Git 或外部变更授权？
