# 阶段二：方案头脑风暴

本阶段由产品开发工作流的入口选择；它围绕已确认的问题生成、比较并收敛候选方案，不代替问题探索或开发需求澄清。

跨阶段的只读、确认和授权规则见[入口的“公共契约”](../SKILL.md#公共契约)；本文件只定义阶段二特有的方案比较与收敛步骤。

## 目标

围绕一个已确认的问题，发散出真正不同的可行方向，再基于明确标准收敛为用户可选择的方案。保留不确定性和取舍，不把推荐方案伪装成用户已确认的需求。

本阶段解决“怎么做”，不代替产品需求探索解决“该解决什么问题”，也不代替需求澄清解决“具体交付什么”。

## 开始前的分流

开始前至少确认以下信息：目标使用者或受益方、要改善的结果、问题/机会陈述，以及已知约束。若其中任一项会实质改变方向且无法从现有资料确定，回到阶段一：产品需求探索。

| 当前未知项 | 应进入的阶段 |
| --- | --- |
| 用户、场景、痛点或机会是否真实存在 | 阶段一：产品需求探索 |
| 已确认问题，但方案、产品形态或架构方向未知 | 本阶段 |
| 已选方案，但权限、数据规则、范围、验收或授权未知 | 阶段三：开发需求澄清 |

## 信息状态

在每次讨论中区分：

- **已确认目标与约束**：用户明确选择的结果、边界、预算、期限或技术限制；
- **已观察事实**：从代码、数据、文档、测试或现有系统中读取到的状态，记录来源；
- **方案假设**：某个方向依赖但尚未验证的前提；
- **候选方案**：用于比较的解法，不等于需求或实施决定；
- **推荐意见**：基于评价标准的判断，仍需用户确认。

不要因现有实现、团队习惯或“最佳实践”而静默排除合理方向。也不要把当前代码或技术偏好写成业务目标。

## 工作流

### 1. 定义要做的决策

先写清本轮需要用户决定什么，例如“以何种方式让销售人员更快找到客户历史记录”。列出：

- 已确认的问题、目标使用者和期望结果；
- 必须满足的限制与非目标；
- 可以安全只读调查的当前事实；
- 仍会改变方向的关键未知项。

发现目标、约束或现有事实互相冲突时，不要自行选择。先解释冲突，再请用户确认，或转回产品需求探索。

### 2. 选择探索深度

按影响范围和不确定性选择适当深度：

| 模式 | 适用情况 | 最低要求 |
| --- | --- | --- |
| 快速发散 | 范围局部、可逆，不改变权限、数据或公共契约的功能或流程改进 | 2–4 个有差异的方向及简短取舍 |
| 受约束设计 | 目标明确，但成本、体验、权限或交付期限有明显权衡 | 明确评价标准、比较表和推荐理由 |
| 架构探索 | 涉及新子系统、数据模型、公共接口、迁移、安全或长期运维 | 只读调查现有架构；说明兼容、迁移、运营和回滚影响 |

不要为了显得全面而生成无意义的方案数量。若实际只有一个合理方向，说明原因及剩余风险。

### 3. 先调查，再发散

在仓库或系统资料可用时，先只读检查相关入口、现有模式、依赖、数据边界、接口和测试。把调查结果标为当前事实，而非未来设计要求。

将方案空间刻意拉开。可根据任务考虑：

- 保持现有流程并局部改善；
- 配置、规则或人工流程，而非新增代码；
- 最小 MVP 与完整体验；
- 复用/集成现有能力与自建能力；
- 单一中心化方案与可扩展的模块化方案；
- 在有意义时包含“不做、延后或缩小范围”。

每个候选方案必须在用户体验、业务流程、技术路径、投入或风险上存在实质差异，不能只是同一方案换名称。

### 4. 具体描述每个方案

每个方案至少包含：

1. 核心思路与适用条件；
2. 用户或系统的主流程；
3. 涉及的边界、依赖与主要改动面；
4. 带来的价值；
5. 成本、风险、缺点和未验证假设；
6. 可用于验证或试行的最小步骤。

不要把细节写到具体实现、字段或接口契约，除非这些细节正是比较方案的必要差异。

### 5. 按共同标准比较

先与用户确认或从已确认目标中推导评价标准，再统一比较。常见维度包括用户价值、覆盖范围、实现成本、上线速度、可维护性、兼容性、权限/隐私风险、可靠性和可扩展性。

使用文字或表格解释权衡。没有可靠数据时，使用定性判断并标注其依据；不要虚构成本、用户数、性能数据或概率。

### 6. 收敛并交接

给出条件化推荐，例如“若优先验证价值，推荐 A；若必须保留现有接口并降低发布风险，推荐 B”。用户的明确选择才成为后续工作的方向。

选定方向后：

- 仍缺业务规则、数据范围、权限、失败语义、验收或执行授权：进入阶段三：开发需求澄清；
- 发现问题本身或优先级并未确认：回到阶段一：产品需求探索；
- 用户仅要建议：止于方案与推荐，不修改工作区或外部系统。

## 提问契约

每轮优先询问一个最影响方案比较的决策主题，例如“更重视首次交付速度还是长期扩展性”。提供 2–3 个具有真实取舍的选项，并说明影响。

可通过安全只读调查确定的技术事实不要询问用户。对业务优先级、风险承受度和方向选择，不要以技术偏好替代用户决定。

## 输出契约

完成一次头脑风暴后，按以下结构输出：

1. **决策框架**：已确认的问题、目标、约束与非目标。
2. **已观察事实与假设**：分别列出来源和不确定性。
3. **候选方案**：每项的主流程、价值、成本、风险与验证方式。
4. **比较与推荐**：评价标准、权衡、条件化推荐和不推荐理由。
5. **待用户决定**：明确需选择的方向或优先级。
6. **后续交接**：说明何时进入需求澄清、继续探索或停止。

方案选择不自动授权原型、文件修改、提交、发布或外部变更。用户要求实施时，先完成适用的需求澄清和授权确认。

## 快速检查

- 是否从已确认的问题开始，而不是从喜欢的技术或功能开始？
- 候选方案是否真正不同且各有适用条件？
- 是否同时写出了收益、成本、风险和未知项？
- 推荐是否依赖显式评价标准，而非伪装成事实？
- 是否把未确认的方案、业务规则与实施授权分开？
