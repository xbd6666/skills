# 阶段三：开发需求澄清

本阶段由产品开发工作流的入口选择；它将已选问题和方向整理为可执行、可验收的开发需求，并明确执行授权。

## 目标

把零散想法逐项澄清为严谨、可执行、可验收的开发需求。先调查可发现的事实，再确认不可代替用户决定的意图；不要把当前实现、常见做法或推荐方案冒充为用户需求。

## 核心流程

按以下顺序工作：

1. **识别任务与交付方式**：判断是只分析、缺陷修复、功能开发、重构、UI 调整或其他开发任务，并提取用户已经说明的执行要求。
2. **标注信息状态与来源**：区分用户确认的需求、已观察事实、建议默认值、待确认项、实施时决定和执行授权。
3. **先做只读调查**：检查适用的项目说明、代码、测试、配置、日志、截图和文档，先解决能够安全发现的技术事实。
4. **评估风险**：判断未知项属于高、中或低风险，只让会实质改变结果的未知项阻塞工作。
5. **选择决策主题**：按影响、未知程度和不可逆性选择当前最重要的待确认项。
6. **逐轮澄清**：更新所有已回答事项，解决证据冲突，再选择下一个决策主题。
7. **检查完成门槛**：根据风险、验收条件和执行授权决定输出需求、继续提问、报告阻塞项或开始实施。

如果请求已经清晰、局部、可逆且不存在中高风险未知项，说明不需要额外澄清，并按用户已经给出的交付与执行要求继续。

## 信息状态与证据

| 状态 | 判定 |
|---|---|
| 用户确认的需求 | 用户明确确认的未来目标、业务规则、范围、限制或验收结果 |
| 已观察事实 | 从代码、测试、日志、截图、配置或文档中读取到的当前状态，必须记录来源 |
| 建议默认值 | 为帮助决策而提出但尚未获得用户接受的方案，不得写成已确认需求 |
| 待确认 | 不同答案会实质改变用户可见结果、权限、数据、兼容性、公共接口、修改范围或验收结论 |
| 实施时决定 | 不改变外部行为，可依据现有架构和项目规范选择的内部技术细节 |
| 执行授权 | 用户明确允许的文件修改、仓库操作或外部状态变更及其范围 |

遵守以下证据规则：

- 只用用户确认或用户指定的权威需求说明确定未来目标。
- 只把代码、测试和运行结果作为当前状态的证据，不用它们替代未来业务意图。
- 为关键事实记录来源；来源可能过期或互相冲突时，说明冲突及其影响。
- 用户描述、需求文档、代码和测试发生实质性冲突时，不要静默选择。先判断冲突描述的是“当前事实”还是“目标行为”，无法消解且会改变结果时转为待确认项。
- 不要重复询问已经回答的问题，也不要询问能够通过安全只读调查确定的技术事实。

## 先调查后提问

在询问文件位置、当前行为、运行环境或项目约束之前，先检查用户提供或工作区中适用的：

- `AGENTS.md`、项目规范和仓库说明；
- 相关代码、测试、配置和接口定义；
- 用户提供的日志、截图、错误信息和文档；
- 可安全执行的只读定位或复现检查。

限制调查范围，只读取完成当前判断所需的内容。只读调查不构成文件修改、仓库操作或外部状态变更授权。

## 风险分级

| 风险 | 典型情况 | 处理方式 |
|---|---|---|
| 高 | 权限、安全、隐私、数据删除或迁移、数据库结构、公共接口、兼容性、不可逆操作或外部状态变更 | 在实施相关行为前取得明确答案和对应授权 |
| 中 | 用户可见行为、修改范围、失败语义或验收结果存在多种合理解释 | 提问确认，或让用户明确接受带影响说明的推荐默认值 |
| 低 | 不改变外部行为的内部实现，或清晰、局部、可逆且符合现有规范的修改 | 归入实施时决定；用户已要求实施时不额外阻塞 |

按“影响程度 × 未知程度 × 不可逆性”选择问题，不机械遵循字段顺序。高风险项优先于交付格式、分支名称等低风险细节。

## 提问契约

默认每轮只处理一个决策主题。每次回复包含：

1. 一句简短的当前理解；
2. 一个最高优先级决策主题；
3. 必要时提供 2–3 个候选答案及其影响。

只有在问题彼此独立，并且用户要求快速确认或多轮往返成本明显较高时，才可以一次提出 2–3 个短问题。相互依赖或中高风险的问题仍然逐项确认。

设计候选答案时：

- 仅在选择确实互斥时要求单选；适合多选或自由输入时明确说明。
- 把推荐项放在前面并标记“推荐”，用一句话说明影响或取舍。
- 候选项只是帮助用户表达，不代表事实或默认授权。
- 用户回答仍有多种实现含义时，继续围绕同一主题澄清。

## 用户无法回答时

不要无限追问，也不要擅自补全：

1. 给出一个推荐默认值，说明采用与不采用的主要影响。
2. 用户接受后，把它记录为用户确认的选择；不要把未接受的推荐写入最终需求。
3. 低风险未知项可以归入实施时决定。
4. 中高风险未知项仍无法确定时，输出已确认内容、阻塞决策和推荐选项，不生成看似完整但不可可靠实施的最终需求。

“按最佳实践处理”只能委托不改变业务语义的内部实现，不能替代业务规则、权限、数据兼容、数据库结构、公共接口或不可逆操作的确认。

## 通用字段

最终需求覆盖或明确标记“不适用”：

- 任务类型；
- 目标；
- 相关位置，或用于定位的现象与入口；
- 当前情况；
- 期望结果；
- 业务规则与关键边界；
- 修改范围与非目标；
- 验收标准；
- 执行方式与授权范围。

未知文件或方法名可以写“需要先定位”，但必须提供足够的现象、入口、错误或操作线索。

## 按任务类型检查

只检查当前任务适用的信息，不机械套用全部条目：

| 类型 | 适用信息 |
|---|---|
| 缺陷修复 | 复现步骤、实际结果、期望结果、运行环境、复现稳定性、可用日志或截图、不能改变的行为 |
| 功能开发 | 使用者与权限、主流程、数据规则、适用的空值、重复、无权限、异常、部分成功或并发边界、允许修改范围、非目标 |
| 重构 | 当前结构问题、必须保持的外部行为、允许修改的内部实现、禁止范围、行为等价验证 |
| UI 调整 | 页面或截图、具体区域、可观察问题、可判断目标、适用交互状态、响应式尺寸、不允许影响的样式 |
| 只分析 | 分析对象、期望输出、明确禁止的文件修改和外部状态变更 |

## 条件式非功能需求

只有在与当前任务相关时检查：

| 领域 | 检查内容 |
|---|---|
| 安全与隐私 | 身份、权限、敏感数据、脱敏、审计、数据保留与合规约束 |
| 性能与容量 | 响应时间、吞吐量、数据规模、超时、限流和资源上限 |
| 可用性 | 可访问性、响应式状态、国际化、时区和错误提示 |
| 可靠性与可观测性 | 日志、指标、告警、重试、幂等、降级和部分失败 |
| 变更安全 | 向后兼容、迁移、回滚和发布限制 |

不要为了完整而制造无意义追问；不适用时明确标记“不适用”。

## 验收标准

把验收标准写成能够客观判定成功或失败的条件，并按需包含：

- 给定输入或前置状态、执行操作和可观察结果；
- 正常路径以及适用的失败、权限和边界路径；
- 自动测试、命令输出、截图或人工验证等证明方式；
- 不允许出现的回归和必须保持的兼容行为；
- 适用的性能、安全、可靠性或可访问性阈值。

避免只写“正常工作”“体验良好”“性能合理”等主观表述。适合时使用“给定／当／那么”结构，但不要机械套用。

## 执行授权

分别确认以下范围，不互相推导：

1. **需求确认**：同意目标、边界和验收标准。
2. **工作区修改授权**：允许在约定范围内修改文件并执行本地验证。用户明确要求“实现”或“修改”时，可以视为该范围内的授权。
3. **仓库与外部变更授权**：创建或切换分支、提交、合并、推送、部署、发送消息、修改远程系统或迁移数据，需要用户明确要求或更高优先级指令授权。

确认需求不自动授权执行，授权工作区修改也不自动授权仓库历史或外部状态变更。

## 完成门槛

满足以下条件后再生成可直接实施的最终需求：

- 目标和期望结果可以客观判断；
- 中高风险业务、权限、数据、兼容和范围决策已经确认或明确不适用；
- 关键证据冲突已经解决，或明确列为阻塞项；
- 验收标准能够证明完成；
- 修改范围、非目标和执行授权明确。

如果用户要求直接实施：

- 存在中高风险待确认项时，先确认相关决策，再修改受影响内容。
- 请求清晰且仅有低风险实施细节时，简要复述范围后按已有工作区修改授权继续，不要求额外确认一份重复需求。
- 涉及仓库历史或外部状态时，单独检查对应授权。

## 最终输出契约

门槛满足后固定输出：

### 需求理解确认

用 2–4 句话复述目标、关键边界、风险和执行方式。

### 整理后的开发需求

写出可以直接交给开发代理的完整需求，使用明确、可观察、可验证的语言。

### 已确认依据与显式假设

列出影响实现的用户决定、关键证据来源和用户已经接受的假设；没有则写“无”。

### 实施时可自行决定

只列不影响业务语义的内部技术选择；没有则写“无”。

### 执行授权

列出允许的工作区修改、仓库操作和外部变更范围；未授权的部分明确写出。

### 未覆盖内容

列出明确排除或暂不处理的内容；没有则写“无”。

中高风险事项仍然无法确认时，改为输出“已确认内容”“阻塞决策”“推荐默认值及影响”，不要伪装成最终需求。

## 示例

用户说：

> 我想在后台加一个导出按钮，把聊天记录导出来，确认后直接实现。

先只读检查相关后台入口、权限模型、现有筛选条件和测试。把找到的角色与当前访问范围记录为“已观察事实”，不要视为未来导出权限。由于导出权限和数据范围属于高风险决策，优先询问：

> 我理解你希望在现有后台增加聊天记录导出，并在确认后实现。导出权限准备沿用现有查看权限，还是需要单独限制？
>
> 1. 沿用现有查看权限（推荐）：规则一致，但任何可查看者都能导出。
> 2. 单独配置导出权限：控制更细，但需要新增权限规则和相应验收。
> 3. 请按角色和数据范围另行说明。

不要提前假定管理员、文件格式、异步任务、审计日志或脱敏规则；先判断这些事项是否适用，再按风险处理。

## 快速检查

- 该请求是否真的存在会改变结果的实质性歧义？
- 是否先调查了能够安全发现的事实？
- 是否把当前实现误写成未来需求？
- 是否记录了关键证据来源与冲突？
- 是否按风险选择了决策主题和提问数量？
- 推荐项是否说明影响且仍保留用户选择权？
- 验收标准能否客观判断成功或失败？
- 需求确认、工作区修改和外部变更授权是否分开？
