# 阶段三：开发需求澄清

把已选问题和方向变成可验收的业务需求。组件职责、接口契约和文件级任务留给阶段四、五；只有实施授权缺失时不重开需求。

## 调查与提问

读取当前任务需要的项目规则、入口、测试、配置和用户材料，先查明事实。说明当前行为与期望行为的差别；证据冲突时保留来源，不用现有实现替代未来意图。

只问会改变业务结果、范围、权限、数据、兼容或验收的未知项：

- 会改变其他问题是否成立的关键决定单独问；彼此独立、能简短回答的问题合并问 2–3 个。
- 用使用场景、可观察结果和主要代价写问题及选项。不要要求用户先理解“幂等”“失败语义”“权限模型”等术语。
- 推荐项置前，但未回答不等于接受推荐。记录已经确认的答案，只追问剩余缺口。
- 没有实质待决项时结束澄清，不为补模板增加轮次。技术实现选择不改变需求时交给后续阶段。

例如：“一次导入中有几条出错，要保留成功的记录，还是这次一条都不保存？”比要求选择事务策略更便于作答。

用户无法决定时，给出推荐及影响，保留阻塞决定；“按最佳实践”不自动决定业务规则。对已明确委托且范围清楚的事项沿用委托。

## 需求成果

覆盖本任务适用的目标、当前问题、期望结果、使用者、业务规则、权限及数据范围、兼容承诺、修改范围、非目标和验收标准。对执行授权单独标明。

按任务补齐必要信息，不套全量清单：

| 任务 | 关键内容 |
| --- | --- |
| 缺陷 | 现象、复现线索、期望结果、环境、不能改变的行为 |
| 功能 | 主流程、使用者、数据规则及适用的失败／边界场景 |
| 重构 | 当前问题、允许改变的内部范围、应保持行为及等价证据 |
| UI | 页面或区域、可观察目标、交互状态、适用屏幕尺寸和语言 |

性能、隐私、可靠性、时区、可访问性、迁移等只在相关时明确。验收描述输入或前提、操作和可判定结果，覆盖实际适用的失败、权限和边界路径；避免“正常工作”等无法判定的表述。

## 定稿与交接

目标、规则、范围及验收足以客观判断，关键业务决定已确认，证据冲突已解决或明确阻塞后，整理正式需求。需求完整不要求实施授权已经取得。

保存 `requirements.md` 前读取[产物与追溯](artifact-contracts.md)，取得该文档写入授权；记录状态、修订、来源与稳定需求标识。文档授权、需求确认和下一阶段选择可以同轮分别询问，已有决定直接沿用。

需要新行为或技术契约时推荐阶段四；已有契约、多个任务需要编排时推荐阶段五；局部明确任务按[直接实施门槛](../SKILL.md#直接进入阶段六)准备检查点。保存后给摘要、路径、需求状态、剩余决定和[阶段交接](../SKILL.md#每轮交付与结尾)，不重复粘贴正文或提前生成下一阶段产物。
