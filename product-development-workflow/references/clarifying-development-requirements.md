# 阶段三：开发需求澄清

本阶段将已选问题和方向整理为可验收的开发需求，并记录执行授权边界；组件职责、接口契约、数据模型、迁移和文件级方案留给后续阶段。

跨阶段的只读、确认、授权和正式产物持久化规则见[入口的“公共契约”](../SKILL.md#公共契约)；本文件只定义阶段三特有的需求澄清与交接要求。

## 先调查后提问

1. 识别任务类型和用户已说明的交付要求；仅需分析诊断时返回入口对应出口。
2. 在最小必要范围内检查 `AGENTS.md`、项目规范、代码、测试、配置、接口，以及用户提供的日志、截图和文档，先解决可安全发现的事实。
3. 按入口[信息与证据](../SKILL.md#信息与证据)记录来源与不确定性。来源过期或冲突时说明影响，区分“当前事实”与“目标行为”；无法消解且会改变结果的冲突转为待确认项，不用当前实现或常见做法替代用户意图。
4. 按入口[必须确认条件](../SKILL.md#安全只读与必须确认条件)区分待确认项与实施时决定，以“影响程度 × 未知程度 × 不可逆性”安排提问。每轮更新已回答事项，不重复询问，也不把可调查的技术事实交给用户决定。

没有实质待确认项时，直接检查下文交接门槛，不增加澄清轮次。

## 提问契约

1. 每轮先检查已有回答与证据，只询问尚未确定且会实质影响需求的事项；已明确的决定不重复确认，可调查的事实先自行调查。
2. 会改变后续问题是否成立、候选答案或整体方向的关键决策，每轮单独询问一个；彼此独立、可以简短回答的问题，每轮合并询问 2–3 个，无须等待用户要求加快。
3. 同一决策主题下，可以提供包含相关规则的完整候选方案，一次说明结果与主要代价；允许用户只修改其中一项，不捆绑无关决定。未回答的事项继续保留为待确认项，不因其他答案已确定而自动采用推荐值。
4. 根据选择关系使用单选、多选或自由输入，需要选项时提供 2–3 个合理选项；推荐项置前并标记“推荐”。推荐值只有经用户明确接受后才能成为已确认需求，不代表事实或默认授权。
5. 只有不同理解会触发入口[必须确认条件](../SKILL.md#安全只读与必须确认条件)、实质改变业务结果、权限、数据、兼容、范围或验收时，才继续澄清需求。仅存在多种技术实现方式且不改变已确认需求时，交给后续阶段处理，不在阶段三反复确认。
6. 每次回答后更新剩余待确认项；已满足交接门槛时立即结束澄清，不为补齐模板或重复复述增加确认轮次。
7. 收口时，可按入口[检查点合并规则](../SKILL.md#检查点可以合并决定分别成立)，在同一条消息中分别列明需求确认、文档写入授权和下一阶段选择，让用户一次逐项回复；已有有效决定直接沿用，各项决定不得互相推导。

白话提问是强制要求，适用于问题、选项及推荐理由：

- 先说用户实际会遇到的场景，再问希望得到什么结果；让不了解技术实现的人也能直接作答，不把内部分析术语、缩写或需求文档字段直接搬进问题。
- 不得要求用户先理解“权限模型”“数据边界”“失败语义”“幂等”等术语才能选择。确实无法避开的名称，先用一句白话解释，再描述可观察的结果；只把术语放进括号或换成缩写不算解释。
- 问题尽量一句话，每个选项一句话，只写结果和一个主要代价；不堆叠背景、风险和后续流程，不转嫁内部实现判断。发送前检查用户能否只凭场景和结果作答，不能则先改写。

例如，把内部需要判断的事项改写成用户能回答的问题：

| 内部判断事项 | 面向用户的白话问题 |
| --- | --- |
| 导出数据边界 | 要导出当前筛选出的记录，还是你有权查看的全部记录？ |
| 导入失败语义 | 一次导入 100 条时，如果几条出错，要保留成功的记录，还是这次一条都不保存？ |
| 重复提交与幂等 | 同一条内容重复提交时，只保留一份，还是允许生成多份？ |

## 用户无法回答时

给出推荐默认值及采用或不采用的主要影响；只有用户接受后才记录为已确认选择。待确认项仍无法确定时，输出“已确认内容”“阻塞决策”“推荐默认值及影响”，不无限追问，也不伪装成完整需求。

“按最佳实践处理”只能委托不改变业务语义的内部实现，不能替代业务规则、权限、数据兼容、数据库结构、公共接口或不可逆操作的确认。

## 需求内容

最终需求覆盖任务类型、目标、定位线索、当前情况、期望结果、业务规则与边界、修改范围与非目标、验收标准、执行方式与授权范围；不适用内容明确标记。

未知文件或方法名可以写“需要先定位”，但必须提供足够的现象、入口、错误或操作线索。

### 按任务类型检查

只检查当前任务适用的信息，不机械套用全部条目：

| 类型 | 适用信息 |
|---|---|
| 缺陷修复 | 复现步骤、实际结果、期望结果、运行环境、复现稳定性、可用日志或截图、不能改变的行为 |
| 功能开发 | 使用者与权限、主流程、数据规则、适用的空值、重复、无权限、异常、部分成功或并发边界、允许修改范围、非目标 |
| 重构 | 当前结构问题、必须保持的外部行为、允许修改的内部实现、禁止范围、行为等价验证 |
| UI 调整 | 页面或截图、具体区域、可观察问题、可判断目标、适用交互状态、响应式尺寸、不允许影响的样式 |

### 条件式非功能需求

只有在与当前任务相关时检查：

| 领域 | 检查内容 |
|---|---|
| 安全与隐私 | 身份、权限、敏感数据、脱敏、审计、数据保留与合规约束 |
| 性能与容量 | 响应时间、吞吐量、数据规模、超时、限流和资源上限 |
| 可用性 | 可访问性、响应式状态、国际化、时区和错误提示 |
| 可靠性与可观测性 | 日志、指标、告警、重试、幂等、降级和部分失败 |
| 变更安全 | 向后兼容、迁移、回滚和发布限制 |

### 验收标准

把验收标准写成能够客观判定成功或失败的条件，并按需包含：

- 输入或前置状态、操作与可观察结果，覆盖正常及适用的失败、权限、边界路径；
- 自动测试、命令输出、截图或人工验证等证明方式；
- 禁止的回归、兼容要求及适用的性能、安全、可靠性或可访问性阈值。

避免只写“正常工作”“体验良好”“性能合理”等主观表述。适合时使用“给定／当／那么”结构，但不要机械套用。

## 需求交接门槛

满足以下条件后再生成最终开发需求：

- 目标、期望结果和验收标准可客观判断，能够证明完成；
- 业务、权限、数据、兼容和范围决策已确认或明确不适用；关键证据冲突已解决或列为阻塞项；
- 范围、非目标和授权状态明确，未授权部分已列出；缺少实施授权不阻止交给阶段四或五。

按入口[分流表](../SKILL.md#七阶段与分流)交给阶段四、五或直接进入阶段六，并取得尚缺的阶段选择和授权；按上文收口规则合并检查点，无须另开一轮重复确认已定内容。技术契约未设计不阻止交给阶段四，需求确认或文档写入不授权实施；已有明确确认与授权时，不重复确认同一份需求。

## 正式产物与对话输出契约

`requirements.md` 按入口[安全持久化规则](../SKILL.md#阶段三至五产物的安全持久化)取得文档写入授权后保存；顶部记录功能名称、`草稿 / 待确认 / 已确认` 状态、修订标识和可复查来源。修订按[下游有效性规则](../SKILL.md#产物修订与下游有效性)处理；直接实施路径可省略独立需求文件。

仅在入口规定的对话产出例外成立时，在对话中完整输出以下结构；正式正文使用可直接交给开发代理的明确、可观察、可验证语言：

| 内容 | 要求 |
| --- | --- |
| 需求理解确认 | 2–4 句话复述目标、关键边界、风险和执行方式 |
| 整理后的开发需求 | 覆盖上文需求内容与验收标准 |
| 后续路径 | 按交接门槛说明下一步；未选定时请求选择，不生成 Spec 或文件级计划 |
| 已确认依据与显式假设 | 用户决定、关键证据及已接受假设 |
| 实施时可自行决定 | 仅列符合入口条件的内部技术选择 |
| 执行授权 | 分别列明允许的工作区、仓库和外部动作及未授权部分 |
| 未覆盖内容 | 明确排除或暂不处理的内容 |

依据、假设、实施时决定或未覆盖内容为空时写“无”。

## 示例

用户说：

> 我想在后台加一个导出按钮，把聊天记录导出来，确认后直接实现。

先只读检查相关后台入口、权限模型、现有筛选条件和测试。把找到的角色与当前访问范围记录为“已观察事实”，不要视为未来导出权限。导出权限和数据范围会改变用户可见结果与数据边界，属于必须优先确认的事项：

> 我理解你希望在现有后台增加聊天记录导出。这个导出按钮准备给哪些人使用？
>
> 1. 能查看聊天记录的人都能导出（推荐）：规则简单，但所有能查看的人也都能下载记录。
> 2. 只有指定人员能导出：控制更严格，但需要额外设置人员范围。
> 3. 我不确定：请结合现有系统给出建议。

不要提前假定管理员、文件格式、异步任务、审计日志或脱敏规则；先判断这些事项是否适用，适用且会改变结果时必须确认。

如果用户已经明确谁能导出、能导出哪些记录，只剩记录顺序和没有记录时的提示需要决定，且两项选择互不影响，可以同轮提问：

> 导出内容已经确定，还需要你选两点：
>
> 1. 文件里的聊天记录怎么排序？A. 最新的放前面（推荐，方便先看最近内容）；B. 最早的放前面（方便按时间顺序查看）。
> 2. 没有符合筛选条件的记录时怎么办？A. 提示“没有可导出的记录”，不下载文件（推荐，避免下载空文件）；B. 仍下载一个空文件。

用户可以一次回复“1A、2A”；只回答其中一项时，仅追问另一项，不重新确认已回答内容。
