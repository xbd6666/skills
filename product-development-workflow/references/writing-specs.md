# 阶段四：编写开发规格

本阶段把已确认需求转为系统行为、组件职责与技术契约，产出经用户审阅的 Spec，供阶段五制定计划；不重新决定业务意图，也不编写文件级任务、代码草稿或提交计划。

跨阶段的只读、确认、授权和正式产物持久化规则见[入口的“公共契约”](../SKILL.md#公共契约)；本文件只定义阶段四特有的 Spec 内容与定稿门槛。

## 输入与分流

需求输入至少应包含：目标与成功条件、范围与非目标、关键业务规则、权限或数据边界、验收标准，以及用户已经作出的决定。记录采用的需求修订，按入口的[“产物修订与下游有效性”](../SKILL.md#产物修订与下游有效性)检查依据是否仍有效；已有信息充分时不要求先补做阶段三。

- 按入口的[“业务需求与技术契约的边界”](../SKILL.md#业务需求与技术契约的边界)分流：仅技术契约待定时留在本阶段；上游业务意图未定或必须改变时，按回退分型进入阶段三。
- 满足入口[“直接进入阶段六”](../SKILL.md#直接进入阶段六)门槛时，不要为了流程强行写 Spec。
- 如果既有系统中需要增加或修改跨模块行为、接口、数据模型、迁移、权限、安全、可观测性或兼容性，完成本阶段后再进入阶段五：编写实施计划。

## 核心流程

1. **说明阶段与依据**：简述已接收的需求交接、需要细化的技术决定，以及不会重开的业务决策。
2. **做定向只读调查**：检查适用项目规范、入口代码、相邻实现、测试、配置和既有契约；只调查能决定 Spec 的最小范围，并记录可复查来源。
3. **建立需求追溯**：按入口[“需求追溯标识”](../SKILL.md#需求追溯标识)沿用或补齐需求编号，映射其行为设计和验证方式；不要把没有来源的新功能混入 Spec。
4. **编写行为与技术设计**：定义流程、状态变化、组件职责、数据流、接口契约、故障语义、兼容策略和验证方式。
5. **处理技术决策**：不改变已确认业务语义的细节，可依据项目证据定为规格技术决定；会显著影响成本、可逆性、性能、安全、公共契约或用户体验的方案，说明取舍并取得用户确认后再定稿。
6. **自检并审阅**：修正冲突、模糊和遗漏；用户确认 Spec 后，才交给阶段五。

本阶段负责确定 Spec 的正文、状态和交接条件；具体路径、冲突检查、最小更新、写后回读及写入边界统一遵循入口的[“阶段三至五产物的安全持久化”](../SKILL.md#阶段三至五产物的安全持久化)。修订已有 Spec 时先按入口修订规则核对旧版留存；Spec 完成本阶段的确认即可恢复自身有效性，下游任务、评审和验证分别复核。

当前代码只能证明现状，不能否定已确认目标。发现上游需求与当前实现冲突时，先记录冲突和影响；不要自行选择一方。实现手段或技术契约的问题留在本阶段处理，只有目标或需求必须重新决定时才回退阶段三。

## Spec 最小结构

删除不适用章节，不保留占位文本：

```markdown
# [功能名称] 规格说明

> 状态：草稿 / 待审阅 / 已确认
> 修订：r1
> 上游需求：[已确认需求文档及采用修订，或可复查的对话交接]
> 依据有效性：有效 / 待复核 / 已失效

## 1. 背景、目标与成功条件
## 2. 范围与非目标
## 3. 当前状态与受影响边界
## 4. 行为规格
## 5. 技术设计与组件职责
## 6. 数据、接口与安全边界
## 7. 兼容性、迁移与运行约束
## 8. 验收场景与验证策略
## 9. 已确认决定、规格技术决定、实施时决定与未决项
## 10. 交给实施计划的约束
```

用“给定／当／那么”或同等可观察的形式描述适用场景。接口、数据模型和组件只定义契约与职责；不要列出具体文件、逐步编码操作、提交命令或任务拆分。

## 定稿与交接门槛

在宣布 Spec 可交给阶段五前，确认：

- 上游修订仍有效，每项需求均映射到 Spec 章节与验证方式，本次修订的下游影响已记录；
- 范围、非目标、权限、数据、公共接口和兼容边界没有被技术细节悄然改变；
- 所有关键行为、失败路径和适用的非功能约束可客观验证；
- 事实、用户决定、技术决定与假设分明，没有会改变实施计划的实质待确认项；
- 用户已审阅确认 Spec；实施授权仍按入口规则处理。

定稿并保存文档后，在对话中输出 Spec 摘要、可点击的文档位置、状态、已确认技术决定、未决项、未覆盖范围和给阶段五的交接说明，不重复粘贴完整正文。仅在入口规定的对话产出例外成立时，才在对话中输出完整 Spec 及相同的交接信息。
