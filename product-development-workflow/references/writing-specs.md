# 阶段四：编写开发规格

本阶段由产品开发工作流的入口选择。它以阶段三已经确认的开发需求为输入，定义系统的技术与行为契约，并产出交给 `writing-plans` 的经审阅 Spec；它不是独立 Skill，也不重新进行产品发现、方案比较或需求澄清。

## 目标

把“做什么、边界和如何验收”的已确认需求，转化为“系统应如何表现、各组件如何协作、实施必须保持什么”的规格说明。Spec 不是需求访谈记录，也不是文件级任务清单、代码草稿或提交计划。

## 输入与分流

阶段三交接至少应包含：目标与成功条件、范围与非目标、关键业务规则、权限或数据边界、验收标准，以及用户已经作出的决定。

- 如果中高风险事项仍会改变用户可见行为、权限、数据、公共接口、兼容性或验收结论，停止定稿并回到阶段三。
- 如果改动清晰、局部、可逆，且不需要新增技术或行为契约，不要为了流程强行写 Spec；按项目约定直接实施。
- 如果既有系统中需要增加或修改跨模块行为、接口、数据模型、迁移、权限、安全、可观测性或兼容性，完成本阶段后再进入 `writing-plans`。

## 核心流程

1. **说明阶段与依据**：简述已接收的需求交接、需要细化的技术决定，以及不会重开的业务决策。
2. **做定向只读调查**：检查适用项目规范、入口代码、相邻实现、测试、配置和既有契约；只调查能决定 Spec 的最小范围，并记录可复查来源。
3. **建立需求追溯**：给每项上游需求稳定标识（如 `R-1`），映射其行为设计和验证方式；不要把没有来源的新功能混入 Spec。
4. **编写行为与技术设计**：定义流程、状态变化、组件职责、数据流、接口契约、故障语义、兼容策略和验证方式。
5. **处理技术决策**：不改变已确认业务语义的细节，可依据项目证据定为规格技术决定；会显著影响成本、可逆性、性能、安全、公共契约或用户体验的方案，说明取舍并取得用户确认后再定稿。
6. **自检并审阅**：修正冲突、模糊和遗漏；用户确认 Spec 后，才交给 `writing-plans`。

只在用户要求编写或保存 Spec 时创建或修改规格文档；该授权不包含代码、测试、提交、推送或外部系统变更。若用户只要求分析或草稿，停在对应产物。

## 信息状态与证据

| 标签 | 含义 |
| --- | --- |
| 已确认需求 | 阶段三中用户决定或权威需求说明的未来行为 |
| 已观察事实 | 从当前代码、测试、配置或文档发现的事实及来源 |
| 规格技术决定 | 不改变已确认业务语义的实现级设计选择 |
| 待确认 | 缺少答案会实质改变结果的事项；定稿前必须清零或退回阶段三 |
| 实施时决定 | 不影响外部契约、可由现有项目规范决定的细节 |

当前代码只能证明现状，不能否定已确认目标。发现上游需求与当前实现冲突时，先记录冲突和影响；无法判定目标或影响时，不要选择一方，标为待确认并回退。

## Spec 最小结构

删除不适用章节，不保留占位文本：

```markdown
# [功能名称] 规格说明

> 状态：草稿 / 待审阅 / 已确认
> 上游需求：[阶段三交接文档或对话摘要]

## 1. 背景、目标与成功条件
## 2. 范围与非目标
## 3. 当前状态与受影响边界
## 4. 行为规格
## 5. 技术设计与组件职责
## 6. 数据、接口与安全边界
## 7. 兼容性、迁移与运行约束
## 8. 验收场景与验证策略
## 9. 已确认决定、规格技术决定、实施时决定与未决项
## 10. 交给实施计划的约束
```

用“给定／当／那么”或同等可观察的形式描述适用场景。接口、数据模型和组件只定义契约与职责；不要列出具体文件、逐步编码操作、提交命令或任务拆分。

## 定稿与交接门槛

在宣布 Spec 可交给 `writing-plans` 前，确认：

- 每项上游需求都映射到 Spec 章节和验证方式；
- 范围、非目标、权限、数据、公共接口和兼容边界没有被技术细节悄然改变；
- 所有关键行为、失败路径和适用的非功能约束可客观验证；
- 当前事实、用户决定、技术决定和假设没有混写；
- 不存在会改变实施计划的实质待确认项；
- 用户已审阅并确认 Spec，且代码或仓库操作仍须另行授权。

定稿后输出 Spec 摘要、文档位置、已确认技术决定、未覆盖范围和给 `writing-plans` 的交接说明。

## 快速检查

- 输入是已确认需求，还是仍需决定的产品或业务问题？
- 当前内容在定义“系统应如何表现”，还是已经越界成文件级实施任务？
- 需求、现状证据与技术设计是否可逐项追溯？
- 是否把任何会影响外部语义的未知项伪装成技术细节？
- 用户是否已经确认这份 Spec 可以成为实施计划的依据？
