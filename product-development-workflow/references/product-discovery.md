# 阶段一：产品需求探索

本阶段由产品开发工作流的入口选择；它的产物是洞察、假设和验证建议，不是已确认需求、实现方案或实施授权。

## 目标

在不把猜测包装成需求的前提下，发现值得解决的用户问题，形成可验证的机会假设，并让用户决定下一步方向。

探索的产物是洞察、假设和验证建议，不是已确认需求、实现方案或实施授权。

## 适用边界

将问题分流到正确阶段：

| 当前未知项 | 使用的 skill |
| --- | --- |
| 用户、场景、真实痛点或价值机会未知 | 本阶段 |
| 已确认问题，但解法、产品形态或架构方向未知 | 阶段二：方案头脑风暴 |
| 已选定方向，但业务规则、范围或验收标准未知 | 阶段三：开发需求澄清 |

用户已经明确“为某类用户解决某个问题，并按既定方案实现”时，不要为了探索而重开问题。若只是内部实现细节未知，直接进入需求澄清或实施。

## 信息状态

始终显式区分以下内容：

| 状态 | 含义 |
| --- | --- |
| 用户陈述 | 用户明确说过的目标、观察或限制 |
| 已观察证据 | 来自访谈、工单、数据、日志、研究资料或实测的事实，并记录来源 |
| 推断 | 基于证据的解释，说明推断链和不确定性 |
| 机会假设 | 需要通过进一步验证的用户问题或价值机会 |
| 用户决定 | 用户明确选择继续、验证、延后或放弃的方向 |

代码、埋点和业务数据可以说明当前行为或结果，不能单独证明用户动机、痛点或偏好。不要编造用户原话、调研结果、用户画像、数据规模或竞品结论。

## 工作流

### 1. 建立探索框架

先用已有信息写出：

- 需要做出的决策，例如“是否值得为一线销售解决客户资料查找问题”；
- 可能的使用者、场景和业务目标；
- 已知限制、可用证据和缺失证据；
- 当前不探索的范围。

只询问会改变探索方向的未知项。优先问“谁在什么场景下要达成什么结果”，不要一开始追问具体功能或技术方案。

### 2. 收集和评估证据

先检查用户提供且可安全读取的资料，例如访谈纪要、反馈、工单、漏斗数据、日志、现有流程、竞品材料或代码。为每个关键结论标明来源和可信度。

按证据强弱处理：

- 直接证据：用户访谈、可复核反馈、行为观察或完整数据；
- 间接信号：访问量、失败日志、内部转述或相邻场景；
- 无证据假设：仅可作为待验证机会，不能作为结论。

没有可用证据时，提出最小研究计划，不要用想象补全。联系外部用户、采集新数据、访问受限系统或改变线上产品，均需用户单独授权。

### 3. 描述问题而非方案

针对每个高价值场景，记录：

- 使用者和触发情境；
- 想完成的任务及期望结果；
- 当前障碍、替代做法和造成的代价；
- 已有证据、反例和未知项。

将“加一个按钮”“做一个 AI 功能”等方案语言还原为待验证的问题陈述。若用户坚持既定方案，也保留其为约束，但不要假装它已证明是最佳解。

### 4. 形成机会假设

使用可证伪的表达：

> 对于 `[使用者]`，当 `[场景]` 时，因 `[障碍]` 难以 `[期望结果]`；我们假设改善 `[结果]` 会带来 `[用户或业务价值]`。

一项机会假设只描述问题与预期价值，不提前锁定 UI、技术架构或功能清单。必要时保留相互竞争的假设。

### 5. 排序并选择验证对象

用与当前目标相关的维度比较机会：用户影响、覆盖范围、证据强度、战略匹配、实现/运营约束和风险。不要制造看似精确的分数；无法可靠量化时，明确其为定性判断。

优先选择“重要且不确定”的机会进入验证。将低价值、缺少证据或超出当前范围的机会明确延后或排除。

### 6. 设计最小验证

为优先机会提出最小、可逆的学习活动，并写清：

- 要验证或推翻的假设；
- 方法与样本/数据来源；
- 通过、失败和不确定的判定信号；
- 隐私、同意、权限和成本限制；
- 所需授权，以及验证后由谁做决定。

验证可以是访谈、可用性测试、原型、数据分析、人工流程试行或受控实验。不要在没有授权时发布、联系客户、写入生产数据或收集敏感信息。

### 7. 设置决策门槛与交接

在探索结束时，请用户明确选择：继续验证、选定一个问题进入方案探索、直接确定方向、延后，或放弃。

- 问题已确认、但解法未知：进入阶段二：方案头脑风暴；
- 问题和方向已确认、但交付边界未知：进入阶段三：开发需求澄清；
- 证据仍不足：保留在本阶段，继续验证。

用户选定问题不等于授权设计方案或修改文件；用户选定方案也不等于授权实施。

## 提问契约

每轮优先处理一个最高价值的不确定性。先简短复述已知信息，再提出一个能显著减少不确定性的问题；必要时给出 2–3 个假设或研究路径，并说明各自影响。

能够通过资料、安全只读检查或验证活动回答的问题，不要转嫁给用户。无法从外部事实得出的价值取舍、目标用户优先级和战略边界，应由用户决定。

## 输出契约

根据当前阶段输出以下内容，并把未知项明确标为未知：

1. **探索框架**：决策、目标用户、场景、范围与限制。
2. **证据与不确定性**：来源、观察、推断和可信度。
3. **机会假设**：问题陈述、潜在价值、反例和待验证点。
4. **优先级判断**：比较依据、暂缓项与原因。
5. **最小验证计划**：方法、判定信号、风险和所需授权。
6. **待用户决定与下一步**：明确交接到头脑风暴、需求澄清或继续探索的条件。

不要输出伪装成最终需求的功能清单。若用户要求立即实现，先指出哪些关键假设尚未验证；只有用户明确接受相应风险或选择方向后，才转入后续阶段。

## 快速检查

- 是否把证据、推断、机会假设和用户决定分开？
- 是否先理解用户任务和痛点，而不是先设计功能？
- 是否给出了可以推翻假设的验证条件？
- 是否避免把间接信号或常见做法当成用户需求？
- 是否明确了探索结果尚未构成实施授权？
