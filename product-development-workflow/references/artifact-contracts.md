# 产物与追溯

阶段三至五保存正式文件，或修改已被下游采用的依据时读取。阶段内容和确认条件由各阶段文档定义；本文件统一管理保存、来源、修订和有效性。

## 保存规则

| 阶段 | 文件 | 写入条件 |
| --- | --- | --- |
| 三 | `requirements.md` | 内容完整后说明路径、内容、非目标和回读方式，取得该文档写入授权 |
| 四 | `spec.md` | 内容、状态、路径确定且无影响正文的实质未决项时直接保存，可先标“待审阅” |
| 五 | `implementation-plan.md` | 内容、状态、路径确定且无影响正文的实质未决项时直接保存，可先标“待审阅” |

保存 Spec 或计划不需要单独的 Markdown 权限；待审阅文件不等于已获用户确认，保存也不授权实施。

- 采用已确认项目根目录及项目约定的文档布局；没有约定时用 `.product-development-workflow/<task-slug>/`。根目录含糊时先确认；任务短标识由当前任务确定，不为命名偏好反复提问。
- 创建前检查同名目录和文件的任务身份。更新前完整读取目标，保留仍有效内容；来源不明、任务冲突、决定未解或并行修改无法安全合并时保留原文件，请用户决定，不另造相似目录绕开冲突。
- 保存后回读标题、状态、修订和关键决定，给出可点击路径。只更新当前获准产物；附带文档、代码、测试与外部动作另按授权处理。
- 澄清、候选比较和未决项处理留在对话，不为每一轮创建文件。用户明确只要对话／非正式草稿、拒绝写入或没有可写工作区时，在对话交付完整正文并说明原因。用户明确要求保存草稿时按其范围处理，未定内容标清，不宣称定稿。

## 来源与追溯

区分用户陈述、已观察事实、推断、用户决定、已确认需求、阶段技术决定、实施结果和验证证据。当前事实不决定未来业务意图，实施结果不替代验收证据。

沿用稳定标识；缺少时，首次需要追溯的阶段为已确认需求补 `R-*` 并关联原文位置或可复查消息和验收标准。有 Spec 时可映射 `R → S → T → V`，否则 `R → T → V`。编号是引用，不新增需求、不强制补建文件，不因排序重编号。

正式产物记录自身修订（如 `r1`）、审阅状态、上游位置与采用修订，以及依据有效性。对话交接保留决定摘要与可复查来源；旧文件没有修订时可采用内容指纹加可取回原文，不为补元信息越权改写上游。

正文或决定改变时递增修订；单改审阅状态、采用修订或有效性等元信息不用增加正文修订。审阅状态与当前依据有效性分开：曾“已确认／可执行／已评审”不保证当前仍有效。

## 产物修订与下游有效性

覆盖已确认或被下游采用的旧内容前，确保它可取回并与被替换内容一致：优先复用固定 Git 提交／blob 或宿主版本；也可在已有授权位置保存原文或有可取回基底的补丁。不需要新建提交或每轮快照。

实际读取并核对留存内容，关联修订及取回位置。只有摘要、哈希、分支名或 `HEAD` 不算可恢复版本；未提交内容不能由不同的已提交内容替代。没有可用位置时保留原文，说明所需最小留存范围并补齐授权后再覆盖。

比较新旧目标、规则、契约、任务依赖和验收，分别处理受影响文档、实施、评审和验证：

| 有效性 | 使用方式 |
| --- | --- |
| 有效 | 与当前依据一致；无语义影响的变化须记录保留依据 |
| 待复核 | 有实质影响或影响不明；暂停依赖它的实施和完成声明 |
| 已失效 | 已确认与新依据不符；旧结果仅作为旧修订历史 |

只影响一部分时保留其余有效部分。恢复条件分别判断：文档完成自身确认／检查并核对新依据即可；实施须核对及必要修改、自检；评审须重新复核受影响部分；验证须取得有效证据。不因保存文档或文件名未变恢复旧结论，也不要求文档等到下游实施后才恢复。

逐项核对新修订的预期结果、范围、文件、动作和验证是否仍被原授权覆盖，只补齐新增部分。无权更新下游文件时在当前任务记录或对话标明其修订与有效性，恢复工作前核对，不另建强制账本。

旧修订已丢失时如实说明，将影响不明的下游标为待复核；可根据新确认的完整依据重新检查并恢复，不能虚构前后比较或旧证据。
