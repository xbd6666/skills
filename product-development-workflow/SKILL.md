# 产品开发工作流

## 目标

用一个入口处理从模糊想法到有证据支持的开发交付。先区分分析诊断与开发阶段，再从最早的关键未知项分流；信息状态与授权按公共契约分别判断。

本目录只有本文件是对外入口。`references/` 下的七个文档是内部阶段能力，不作为独立 Skill 安装或调用。每次只读取当前阶段文档；跨阶段共用的路由、确认、授权、验证和持久化规则以本文件为唯一权威来源。

## 阶段外分析与诊断

用户明确只要求分析、诊断、审查、解释、状态检查或报告，且没有要求形成需求、Spec、计划、实施或验收产物时，直接进入本出口，不要求用户从七阶段中选择，也不为执行开发阶段而读取 reference。

- 默认只执行下文定义的安全只读调查，不创建正式开发产物，不修改工作区、仓库或外部状态。
- 静态证据不足、需要运行测试、构建、启动服务或临时复现才能判断原因时，仍留在本出口。先说明要验证的假设、命令、目标、临时产物及服务的启动、停止和清理范围，再按“验证动作与授权”复查已有授权；缺少覆盖时取得相应授权后才执行。用户明确要求只读或禁止运行时，保持只读并说明未能证明的内容。
- 动态诊断授权只覆盖列明的复现动作及其副作用；临时脚本和产物限于获准位置，不自动授权改写项目源文件、测试、快照、锁文件或实施修复。真实数据和外部系统仍按公共授权规则单独处理。
- 结论使用 `分析完成`、`无需变更`、`阻塞` 或 `建议进入后续阶段`。证据表明现状已满足目标时，以 `无需变更` 结束，不强迫进入阶段六或七。
- 发现需要修复项目、改变需求或交付阶段产物时，说明证据、建议的阶段和预期产物；取得阶段选择及适用授权前不实施。不因运行诊断命令而转入阶段六或七，也不把复现结果当成修复或验收结论。
- 用户明确要求任一阶段的专属产物、修改项目文件或验收交付时，不使用该出口规避对应阶段和授权。

## 七阶段与分流

| 分流判据 | 进入阶段 | 读取的内部文档 | 产物与交接门槛 |
| --- | --- | --- | --- |
| 用户问题或价值机会尚未确认 | 阶段一：产品需求探索 | [探索](references/product-discovery.md) | 证据、机会假设和最小验证计划；确认问题或明确接受已披露的证据限制后交接，否则继续验证 |
| 问题已确认，产品形态、流程或技术方向未知 | 阶段二：方案头脑风暴 | [方案](references/brainstorming.md) | 候选方案与取舍；用户选定方向或明确接受带影响说明的推荐后，按剩余缺口交接 |
| 问题与方向已选，业务规则、权限、数据边界、范围或验收未知 | 阶段三：开发需求澄清 | [需求](references/clarifying-development-requirements.md) | 已确认需求及授权边界；目标、关键业务与数据边界、范围、非目标和验收标准明确后交接 |
| 需求已确认，系统行为、技术职责、数据或接口契约、异常、兼容或验证策略未知 | 阶段四：编写开发规格 | [Spec](references/writing-specs.md) | 用户已审阅确认、无实质未决项的 Spec；允许起草计划后交给阶段五 |
| 需求或 Spec 已确认，文件级改动、任务依赖、测试步骤或执行方式未知 | 阶段五：编写实施计划 | [计划](references/writing-implementation-plans.md) | 覆盖需求、适用 Spec、依赖与验证的计划；无影响用户可见结果的未决项且实施授权齐备后交接 |
| 计划已就绪且已授权修改工作区，实施尚未完成 | 阶段六：执行开发计划 | [执行](references/executing-development-plans.md) | 完成任务级自检与适用评审的变更；或有可复查阻塞证据、必须依赖新授权或外部条件才能继续的未完成任务 |
| 实施已结束或满足阻塞交接条件，需要判断交付状态 | 阶段七：验证与验收 | [验收](references/verification-and-acceptance.md) | 带证据的交付结论、遗留项和验收交接；仅 `已通过开发验收` 可以声称开发交付完成 |
| 满足[直接进入阶段六](#直接进入阶段六)的全部门槛 | 直接进入阶段六 | [执行](references/executing-development-plans.md) | 省略不必要的上游产物，仍须实施、自检、适用评审和阶段七验收 |

若多个未知项同时存在，从最早且最影响方向的一项开始。发现先前假设不成立、问题并未确认或用户改变目标时，回退到适用的前一阶段。

交接须满足当前阶段的专属门槛，并按下文确认阶段选择；不必逐一经过七阶段。阶段三完成后，需新增技术或行为契约时交给阶段四；无需新契约，但多任务、文件、依赖或检查点需要独立计划时交给阶段五；局部明确任务按直接实施门槛处理。

### 业务需求与技术契约的边界

阶段三确定目标、业务规则、权限与数据范围、兼容承诺、交付范围和验收标准；阶段四定义实现这些已确认需求的系统行为与技术契约。接口形态、数据模型或故障处理等技术事项尚未确定时，留在阶段四，并按公共契约确认有实质影响的技术取舍。只有上游业务意图仍不明确，或技术可行性迫使上述需求改变时，才按回退分型进入阶段三。技术方案需要用户确认本身不是回退理由。

### 信息缺口与执行授权分开判断

阶段按尚缺的需求、技术契约或计划信息选择，执行授权按对应检查点建立。仅缺实施授权不是进入或回退阶段三的理由，也不要求重做已充分且有效的需求、Spec 或计划。

仅差阶段六选择或授权时，按下文检查点列明范围、非目标、验收与验证方式，可合并请求。两者成立前保留现有产物，只继续必要的安全只读调查。

### 阶段选择由用户确认

明确的阶段外分析与诊断任务自动进入对应出口；阶段六到七按下文[自动衔接规则](#阶段六到七自动衔接)处理。除此之外，在首次分流或准备进入尚未确定的下一阶段时，先做必要的安全只读调查，再向用户提供 2 至 3 个互斥选项：

- 将拟进入的阶段放在第一项并标记为 `（推荐）`，用一句话说明依据和选择后的产物；
- 只列真正合理的相邻阶段、留在当前阶段或暂不继续等备选，不为凑数列出全部七个阶段；
- 宿主支持结构化选项时优先使用；否则使用简短编号选项。用户仍可明确指定未列出的阶段。

用户选择前，只能继续支持分流所需的安全只读调查；不得声称已进入推荐阶段，不得读取该阶段 reference、输出该阶段正式产物或改变工作区及外部状态。

若用户已明确指定阶段、要求该阶段产物或确认交接建议，不重复询问。初始请求中的“修改”“修复”“实现”“帮我处理”等措辞不视为阶段六选择；实施授权另按[对应检查点](#阶段六实施授权)建立。

回退按是否需要新的用户决定分型：

- **程序性回退**：证据已经唯一确定上游产物存在错误，目标阶段也唯一，且回退本身不引入新的方向或范围选择时，直接把该阶段设为当前阶段、读取对应 reference，并在下一次输出开头说明证据和回退依据，不重复弹出阶段选项。
- **目标性回退**：去向存在多个合理选择，或回退会重新决定问题、方向、业务规则、范围或验收时，按本节提供 2 至 3 个互斥选项并由用户确认。

回退只改变当前阶段，写入和验证仍须满足对应授权；不得在代码中静默改变计划、Spec 或业务决定。

### 阶段六到七自动衔接

阶段六达到分流表及其 reference 的正常或阻塞交接门槛后，自动切换到阶段七，说明依据并读取验收 reference，不再请求阶段选择。普通执行、直接实施和微小变更均适用。用户明确要求实施后停止或暂不验收时，记录阶段七尚未进行，不声称开发交付完成。

自动衔接只确定下一阶段，不扩大验证或写入授权。按“验证动作与授权”复查覆盖范围；缺少授权时只请求新增或改变的部分，已覆盖的动作及安全只读检查可以继续。用户仅禁止某个验证动作时，停止该动作并披露未验证项，不据此省略整个阶段七。

## 公共契约

### 信息与证据

共用信息状态只在此定义；各阶段 reference 只补充本阶段增量和判例：

| 状态 | 统一含义 |
| --- | --- |
| 用户陈述 | 用户明确说过的目标、观察、限制或请求；未经确认的描述不自动成为未来需求或授权 |
| 已观察证据 | 从文件、代码、日志、测试、配置、数据或实测读取的当前事实，并记录可复查来源 |
| 推断 | 基于证据形成的解释，必须说明依据和不确定性，不能伪装成事实 |
| 用户决定 | 用户对问题、方向、规则、范围、验收或后续阶段作出的明确选择 |
| 已确认需求 | 用户决定或用户指定的权威需求说明所确定的未来行为 |
| 阶段决定 | 机会假设、候选方案、规格技术决定和计划技术决定；其具体含义由当前阶段 reference 补充 |
| 实施结果与验证证据 | 前者是实际改动，后者是当前、直接且可复查的完成证明，二者不得互相替代 |
| 执行授权 | 用户在适用检查点后明确允许的文件、动作、验证、仓库或外部状态范围 |

代码、日志、测试和现有文档只能证明当前状态，不能替代未来业务意图。

### 需求追溯标识

已有稳定需求标识时直接沿用；尚未编号时，由首次建立追溯映射的阶段为已确认条目补齐本任务内唯一、稳定的标识，例如 `R-1`，并关联原始文档位置或可复查消息，以及对应验收标准。阶段三未编号、跳过 Spec 或直接实施时，均由当前需要映射的阶段补齐，不因缺编号回退或强制补建上游产物。

新编号只是引用别名，不新增需求，也不要求重新确认已定内容。编号与来源映射保存在当前获准写入的产物、任务记录或可复查对话中，不因此改写未授权的上游文件；不因排序或表述调整重编号，新条目使用未占用的编号。

### 安全只读与必须确认条件

安全只读调查限于读取、搜索、比较现有文件、状态、差异和日志，不改变工作区、仓库、进程持久状态、数据库或外部系统。可能产生状态变化的操作按[验证动作与授权](#验证动作与授权)分类。

不同答案会实质改变下列任一事项时，必须取得明确答案及对应授权，不得静默采用推荐值：

- 用户可见结果、业务规则、权限或数据范围；
- 数据结构、迁移、公共接口、兼容性、安全或隐私；
- 外部系统、不可逆或破坏性状态；
- 修改范围、显著成本、验收结论或阶段产物。

只有同时满足以下条件的事项才能作为实施时决定：位于已确认范围内、可逆、不改变外部状态，并且不改变公开行为、契约、安全、数据语义或验收结论。

涉及跨模块行为、公共契约、权限、安全、数据迁移、不可逆状态，或由独立代理实施的任务，在宿主支持时使用独立评审；其他任务由当前代理做明确的二次复核。宿主不支持独立评审时，报告替代复核及其限制。

独立评审要求可以由覆盖当前变更且仍有效的既有独立评审满足，不因阶段切换重复发起相同评审。阶段七按[“既有评审结论的复用”](references/verification-and-acceptance.md#既有评审结论的复用)核对条件与覆盖范围；实施者自检不能作为独立评审复用。

### 检查点可以合并，决定分别成立

可在同一条消息中请求多个确认：逐项编号并说明对象、范围、非目标和后续动作，让用户逐项同意、拒绝或修改。产物确认、阶段选择、实施授权、仓库操作与外部变更分别成立，不能互相推导。

Spec 确认与进入阶段五可以合并询问；完整计划、修改范围、非目标和验证方式已经展示时，计划确认与阶段六实施授权也可以合并询问。用户回复“确认计划并按列明范围实施”等明确语句时，两项决定分别成立；仅回复含糊的 `确认` 且上下文存在多个待确认事项时，不得扩大授权，继续确认具体对象。

新增范围、Git 历史操作、远程写入、发布、部署、生产验证或其他外部状态变化仍分别取得授权，不能为减少往返而静默合并。

### 直接进入阶段六

以下信息与改动条件均满足时，可以省略独立需求、Spec 和实施计划：

- 目标、关键业务与数据边界、范围、非目标和验收标准均明确，没有会改变用户可见结果、权限、数据、兼容、公共契约、安全或验收结论的待确认项；
- 改动局部、可逆，现有项目规范和模式足以指导实施，无需新增技术或行为契约，独立计划也不会增加执行清晰度或可追溯性。

仍须完成安全只读调查，反馈拟修改范围、非目标与验证方式，并取得[阶段六实施授权](#阶段六实施授权)，之后才能实施。实施时决定、适用评审和阶段七验收均不省略；不符合下述快捷通道时，按普通检查点完成阶段选择与授权。

#### 微小变更快捷通道

满足上述信息与改动条件，并符合以下额外限制时，可合并阶段选择、变更契约确认与实施授权：

- 不超过 3 个手写文件，测试和文档计入；排除生成物、锁文件、迁移、CI/CD、部署或生产配置；
- 不改变公共接口或契约、业务规则、权限、数据、安全或兼容语义，不访问外部系统或真实数据；文字已明确且不改变业务含义的展示文案修正适用；
- 能预先列明少量本地验证命令及其副作用。

只读调查后，在同一消息中分别列明：`A` 阶段六推荐及合理备选，`B` 当前理解、范围、非目标和验收结果，`C` 拟修改文件或边界、验证命令与授权请求。用户后续肯定回复须唯一覆盖 `A/B/C`；随后读取执行 reference，并按[自动衔接规则](#阶段六到七自动衔接)完成验收，给出精简且证据完整的报告。

任一条件不成立即退出快捷通道，说明原因并重新分流；含糊回复及尚未取得的授权不能覆盖新范围。

### 阶段六实施授权

阶段六工作区修改授权必须依次建立：

1. AI 完成必要的安全只读调查，反馈当前理解、拟修改范围、非目标和验证方式；
2. AI 明确进入授权检查点，说明尚未实施，并针对已说明的范围请求工作区修改及本地验证授权；
3. 用户在后续消息中以 `确认计划并开始实施`、`开始执行`、`按此修改`、`同意实施` 等能够唯一指向该检查点的肯定命令回复。

用户首次提出任务时，无论语气或动词如何，都只是在描述期望结果。阶段选择、需求确认、Spec 确认、计划确认以及阶段四、五产物写入均不自动构成阶段六授权。授权只覆盖检查点列出的文件、动作和验证；范围变化时重新确认。

取得授权后，在首次实施写入前说明当前阶段、授权依据和覆盖范围。无法指出对应检查点及用户后续肯定回复时，不得修改生产代码、测试或其他实施文件。

### 验证动作与授权

进入阶段七、在其他阶段运行验证或执行阶段外动态诊断前，按实际副作用分类：

| 类别 | 典型动作 | 授权规则 |
| --- | --- | --- |
| 只读本地检查 | 读取文件、状态、差异和既有日志 | 可在安全只读范围内直接执行 |
| 有本地副作用的验证 | 构建、测试、依赖恢复、启动服务、生成临时报告或缓存 | 必须有可复查且覆盖命令、范围和副作用的本地验证授权；否则先说明并请求 |
| 更新工作区结果 | 更新快照、生成受版本控制文件、改写锁文件或正式报告 | 必须有覆盖目标文件的工作区修改授权 |
| 外部或真实状态验证 | 真实数据库、远程服务、生产数据、部署、线上冒烟或发送消息 | 必须单独说明目标和影响并取得授权 |

分类不互斥；一个动作命中多类时，必须同时满足全部适用授权。任一所需授权缺失时，不执行该组合动作，只可执行已经安全拆分且授权完整的部分。

阶段六授权明确包含指定本地测试时，紧接的阶段七在命令、目标和范围不变时可以复用该授权。独立进入阶段七、新会话中无法复查授权，或验证动作已经变化时，不得推断授权。无法判断某个验证是否会写入或访问外部状态时，先做只读配置检查；仍不确定则停止并说明。

授权复用与证据复用分别判断；已有结果是否仍能支持当前结论，由阶段七按其证据条件核对，不能仅凭授权仍有效沿用旧结果。

### 阶段三至五产物的安全持久化

阶段三至五把过程讨论与正式交接产物分开。正式文件名固定为 `requirements.md`、`spec.md` 和 `implementation-plan.md`：

1. 先确定已确认的项目根目录。文件位置优先遵循项目规范或现有文档布局；没有适用约定时，使用 `.product-development-workflow/<task-slug>/`。多根工作区或根目录不明确时先确认目标根目录。
2. `<task-slug>` 是任务的短标识。创建目录前检查同名目录是否属于同一任务；语义冲突时停止并请求用户决定，不另造含糊的重复目录。
3. 阶段三形成完整 `requirements.md` 前，说明路径、拟记录内容、非目标和验证方式，并取得仅针对该文档的工作区修改授权。
4. 阶段四 Spec 或阶段五计划的内容、状态和路径确定，且不存在会改变正式产物的实质未决项时，首次写入前说明阶段与目标路径，然后直接创建或更新对应文件，不申请单独的 Markdown 写入权限。
5. 更新前完整读取目标文件，确认它属于同一任务且内容来源清楚；保留仍有效内容，只修改必要章节。已明确被当前决定替代的旧决定按下文修订规则更新；来源不明、决定之间的冲突尚未解决或存在无法安全合并的并行修改时，停止覆盖并请求用户决定。
6. 直接持久化不授权破坏性覆盖，也不授权其他文档、生产代码、测试、Git 历史、部署或外部状态变更。
7. 写入后回读文件，确认路径、状态、标题和关键决定与本轮产物一致。

澄清、候选选择、草稿审阅和未决项处理留在对话中，不为每轮交流创建新文件。只有用户明确要求仅在对话中产出、明确拒绝文档写入、没有可写工作区，或任务明确止于非正式草稿时，才在对话中输出完整 Markdown 产物。

### 产物修订与下游有效性

正式需求、Spec 和计划在头部记录修订标识，例如 `r1`；正文或关键决定更新时递增，仅更新审阅状态、依据有效性或采用修订等元信息不单独增加正文修订。下游同时记录上游位置与所采用的修订，不能只引用固定文件名。对话交接使用可复查的消息引用和决定摘要；直接实施不为此补建独立文件。旧文档缺少标识时，可用内容指纹标识采用基线，但仍须保留可取回的内容；仅在具有对应写入授权时补充元信息。

覆盖已确认或已被下游采用的正式修订前，先确保旧内容可以取回：

- 优先复用与被替换内容一致的 Git 提交或 blob、宿主保留版本；也可在已有授权覆盖的位置保留完整内容，或保留有可取回基底的可复原补丁。不要求新建 Git 提交或为每轮讨论创建快照。
- 在现有修订或任务记录中关联修订标识与固定版本的取回位置，Git 使用具体提交或 blob 标识，不能只引用分支或 `HEAD`；实际读取并核对内容后再覆盖。未提交内容不能用与其不同的已提交版本代替；只有修订号、指纹、摘要或不可复查的临时上下文不算留存。没有可用留存位置时，保留原文件与拟议修改，说明最小留存位置和写入范围，只补齐缺少的授权后再更新。
- 旧修订已经丢失且无法补证时，不虚构前后比较。将影响不明的下游标为 `待复核`；可以按新确认的完整依据重新检查受影响范围、更新产物并取得当前证据，恢复后续工作。无法复查的旧结论仍只保留为未获补证的历史记录。

产物审阅状态与依据有效性分别记录：`已确认`、`可执行`、`已评审` 等状态只描述当时采用的依据；当前依据有效性为 `有效`、`待复核` 或 `已失效`。修订按以下规则处理：

1. 比较修订前后的目标、规则、契约、任务依赖和验收方式，列出受影响的下游产物、实施任务、评审和验证结论。仅排版或拼写修正等经核实无语义影响的变更，记录比对依据后可保留原有效性。
2. 有实质影响或尚不能确定影响的部分标为 `待复核`，停止依赖它的实施及完成声明；已确认与新依据不符的部分标为 `已失效`。旧结果保留为对应旧修订的历史证据，未受影响的部分不一并作废。
3. 按回退规则更新受影响产物，分别记录采用的新修订及恢复依据。文档完成自身所需的确认或自检、核对上游依据后即可恢复 `有效`，不等待下游实施；实施结果在与新依据核对并完成必要修改、自检后恢复，但评审仍待完成；评审结论需完成相应复核，验证结论需按验证规则取得相应证据，才能分别恢复。未受影响且已记录保留依据的部分沿用原结论；不能因文档保存或文件名未变恢复受影响的旧结论。
4. 将新修订要求的预期结果、范围、文件、动作和验证逐项对照原授权；只复用仍被覆盖的部分，新增或改变的授权范围重新确认，不能仅凭文件名相同沿用授权。
5. 失效、保留与恢复依据优先记入现有任务记录或宿主工具。无权改写下游文件时，在当前记录或对话中明确标明其修订和有效性，不越权更新文件；恢复实施或验收前重新核对这些记录与当前产物。

## 输出要求

阶段尚未确认时，先说明推荐阶段和依据并提供选项；阶段已经确认时，先说明当前阶段和依据。阶段外分析与诊断输出证据、结论、未覆盖范围和适用的后续建议；执行过动态诊断时一并说明授权覆盖、实际副作用及遗留状态。阶段内只输出已选阶段要求的产物，并标示证据来源、假设、用户决定、未覆盖范围和所需授权。

正式产物按安全持久化规则处理；阶段七只判定开发交付，后续仓库与外部操作仍遵循公共授权规则和适用流程。

## 快速检查

- 当前出口或阶段是否正确，所需用户决定是否已经成立？
- 写入、验证及其组合副作用是否均在可复查的授权内？
- 采用的修订、下游状态和证据是否仍有效，足以支持当前结论？
