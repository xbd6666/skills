# 产品开发工作流

## 目标

用一个入口处理从模糊想法到有证据支持的开发交付。先判断当前最早的关键未知项，再只进入一个阶段；不要把机会假设、候选方案、已确认需求、技术规格、实施计划、完成证据和执行授权混为一谈。

本目录只有本文件是对外入口。`references/` 下的七个文档是内部阶段能力，不作为独立 Skill 安装或调用。每次只读取当前阶段文档；本工作流不依赖外部 Skill 才能完成阶段五至七。

## 七阶段与分流

| 当前需要做出的决定 | 进入阶段 | 读取的内部文档 | 本阶段产物 |
| --- | --- | --- | --- |
| 是否存在值得解决的用户问题或机会 | 阶段一：产品需求探索 | references/product-discovery.md | 证据、机会假设和最小验证计划 |
| 已确认问题，但产品形态、流程或技术方向未知 | 阶段二：方案头脑风暴 | references/brainstorming.md | 有取舍的候选方案和用户选择 |
| 已选问题与方向，但业务规则、权限、数据边界、范围或验收未知 | 阶段三：开发需求澄清 | references/clarifying-development-requirements.md | 可执行、可验收的开发需求及授权边界 |
| 需求已确认，但系统行为、技术职责、数据或接口契约、异常、兼容或验证策略未知 | 阶段四：编写开发规格 | references/writing-specs.md | 经审阅的技术与行为规格说明 |
| 需求或 Spec 已确认，但文件级改动、任务依赖、测试步骤或执行方式未知 | 阶段五：编写实施计划 | references/writing-implementation-plans.md | 可执行、可追溯且经自检的文件级计划 |
| 计划已就绪且已授权修改工作区，但代码、测试或文档尚未完成 | 阶段六：执行开发计划 | references/executing-development-plans.md | 已实施并经过任务级自检与适用评审的变更 |
| 实施已结束，但尚无新鲜证据证明符合需求、质量要求和验收标准 | 阶段七：验证与验收 | references/verification-and-acceptance.md | 带证据的完成结论、遗留项和验收交接 |
| 目标、范围和验收均清晰，且修改局部、可逆、低风险 | 直接进入阶段六 | references/executing-development-plans.md；完成后读取阶段七文档 | 简短复述范围后实施并验证 |

若多个未知项同时存在，从最早且最影响方向的一项开始。发现先前假设不成立、问题并未确认或用户改变目标时，回退到适用的前一阶段。

## 统一工作规则

1. 先区分用户陈述、已观察证据、推断、机会假设、候选方案、用户决定、已确认需求、规格技术决定、计划技术决定、实施结果、验证证据和执行授权。
2. 先做必要的安全只读调查；不要把代码、日志、现有实现或常见做法写成未来业务意图。
3. 每轮优先处理一个会实质改变结果的决策主题。能从资料或只读检查确定的事实，不转嫁给用户。
4. 在每个阶段结束时明确列出仍未知的事项、所需用户决定和下一个阶段；不得静默跳阶段。
5. 将需求确认、Spec 确认、计划确认、工作区修改授权、仓库操作授权和外部状态变更授权分别处理。选定问题、方案、技术设计或计划不等于允许实施；完成开发也不等于允许提交、合并、推送或部署。

## 执行方式

1. 用上表判断当前阶段，并只读取对应的内部文档。
2. 完整遵循该阶段文档中的调查、提问、输出和安全要求；不要同时加载或混用其余阶段的详细流程。
3. 达到阶段交接门槛后，向用户说明可进入的下一阶段及仍需的决定或授权。
4. 清晰、局部、可逆且不需要新增契约或文件级计划的工作，可在相应工作区修改授权下直接进入阶段六；任何实施路径都必须进入阶段七，才能声称完成。
5. 阶段六发现计划错误时回到阶段五；发现 Spec 错误时回到阶段四；发现业务意图或边界错误时回到阶段三或更早阶段。不得在代码中静默改变上游决定。

## 阶段交接门槛

- 阶段一到阶段二：用户已确认要解决的问题或明确接受在指定风险下继续；验证不足时留在阶段一。
- 阶段二到阶段三：用户已选择方向，或明确接受带影响说明的推荐方向；方案仍只是候选时不得伪装成需求。
- 阶段三到阶段四：目标、关键业务与数据边界、范围、非目标和验收标准已经确认；阶段四只细化技术与行为契约，不重新决定业务意图。
- 阶段三到阶段五：需求已确认且不需要新增技术或行为契约，但工作涉及多个任务、文件、依赖或检查点，独立计划能降低实施风险。
- 阶段四到阶段五：Spec 已审阅、没有实质未决项，并允许在对话中起草计划；保存计划文件需要相应工作区修改授权。
- 阶段五到阶段六：计划已覆盖需求与适用的 Spec、任务依赖和验证方式，没有会改变用户可见结果的未决项，并已取得约定范围内的工作区修改授权。
- 阶段六到阶段七：计划内任务已经实施并完成任务级自检与适用评审；或者未完成项已有可复查的阻塞证据，且必须依赖新授权或外部条件才能继续，以便阶段七形成阻塞报告。此时仍不得声称整体完成。
- 阶段七形成结论：基于新鲜证据输出 `已通过开发验收`、`待用户验收`、`条件通过`、`未通过` 或 `阻塞`，并如实披露失败、遗留项和剩余条件。
- 阶段七到已完成开发交付：只有状态为 `已通过开发验收` 时成立；其余状态只能结束本轮验证、请求验收或回到相应阶段，不能声称开发交付完成。
- 直接进入阶段六：目标、关键业务与数据边界、验收标准和修改授权均已明确，且修改局部、可逆，不需要新增技术或行为契约及独立实施计划。低风险内部细节可由项目规范决定，但仍须进入阶段七。

## 输出要求

始终先说明当前所处阶段和依据。随后仅输出该阶段要求的产物，并清楚标示证据来源、假设、用户决定、未覆盖范围和所需授权。

若用户只要求分析、探索、需求、Spec 或计划，止于相应阶段的产物，不超出已授权范围修改工作区、仓库或外部系统。阶段七只判定开发交付；提交、合并、推送、发布、部署和生产验证仍需单独授权及适用流程。

## 快速检查

- 当前是在确认要解决什么、比较怎么做、澄清交付边界、定义契约、编写计划、实施，还是验证验收？
- 当前结论是机会假设、候选方案、开发需求、Spec、实施计划、实施结果，还是有证据的完成结论？
- 是否把事实、推断、用户决定、技术决定、实施结果和验证证据分开？
- 是否从最早的关键未知项开始，而不是直接假定方案、需求或技术设计？
- 是否在进入实施和外部变更前分别获得了与风险相称的确认和授权？
- 是否只在读取新鲜验证证据后声称完成？
