# 产品开发工作流

一次交付用户当前已选阶段的成果。普通首次改动请求先交付只读调查、需求理解和可供确认的阶段／实施检查点，取得后续实施确认后才交付实现及验收。已指定方案或文档等阶段产物、已有有效授权，或用户明确改变确认方式时，直接按对应约定推进。显式调用和自动匹配本技能都采用这个交付范围；七阶段按需要使用，不要求从头走完。

本文件是唯一公开入口，负责分流与共同边界。阶段文档只定义该阶段的成果；授权和产物细则按下文链接加载，不默认读取全部文件。没有读取本文件时，不声称已执行本技能。

## 工作约定

- **先区分需求与授权。** 新开发请求先做必要的安全只读调查，反馈需求理解、推荐阶段和实施授权状态。需求足够具体、文件很少或改动可逆，都不替代实施检查点。
- **先反馈，后实施。** 本工作流默认约定：说明修改范围、非目标、验收与本地验证后，取得用户后续肯定回复才修改代码、测试或其他实施文件。缺少该回复时，反馈检查点并结束本轮；不边询问边实施。
- **沿用有效决定。** 已有明确、可复查且仍覆盖本次工作的阶段选择和授权直接沿用，在该范围内持续推进到约定结果。只补齐新增缺口，不重复索要同一确认。
- **尊重用户当前指令。** 用户明确要求只读、先给方案、暂不验收或明确改变上述确认方式时，按其指令执行。普通“修改／修复／实现”描述目标，本身不表示取消检查点；明确的“本次直接实施，无需再确认”则是工作方式变更。技能不覆盖用户明确指令或宿主权限。
- **先证据，后结论。** 当前代码、日志和文档只能证明现状；推断、推荐与用户已确认的未来行为分别表述。只读调查不改变文件、进程持久状态或外部系统。

## 七阶段与分流

先判断用户要交付什么，再看最早的关键缺口；不要仅凭“分析”“需求”“方案”等单个词分流。

| 当前要解决的问题 | 阶段与按需读取 | 本阶段结果 |
| --- | --- | --- |
| 谁在什么场景遇到值得解决的问题？ | 一：[产品需求探索](references/product-discovery.md) | 有来源的问题假设、最小验证与取舍 |
| 问题已明确，用哪种产品、流程或技术方向解决？ | 二：[方案头脑风暴](references/brainstorming.md) | 有差异的方案、推荐与待选方向 |
| 方向已选，用户应得到什么结果，范围与规则是什么？ | 三：[开发需求澄清](references/clarifying-development-requirements.md) | 可验收的业务需求与边界 |
| 需求已明确，系统行为和技术契约如何定义？ | 四：[编写开发规格](references/writing-specs.md) | 行为、职责、接口与验证契约 |
| 需求及必要契约已明确，如何拆成可执行任务？ | 五：[编写实施计划](references/writing-implementation-plans.md) | 文件职责、任务依赖与验证方式 |
| 计划或直接实施条件就绪，且已取得实施授权 | 六：[执行开发计划](references/executing-development-plans.md) | 已实施、自检和评审的变更，或可复查阻塞 |
| 实施交接或用户明确要求验收 | 七：[验证与验收](references/verification-and-acceptance.md) | 验收项证据、交付状态与遗留条件 |

### 分流与阶段选择

用户已指定阶段、明确要求其专属产物或接受交接建议时，视为该阶段已选，不再询问同一选择。例如“这个新功能如何实现，先分析再给方案”已经要求方案产物；问题清楚时进入阶段二，调查是形成方案的方法。方向尚未选择时，推荐意见仍是候选。

用户尚未选定阶段、也没有明确要求可确定阶段的专属产物时，完成足以分流的只读调查，说明推荐阶段和依据，给出 2–3 个确实合理的互斥选项，推荐置前。选择前状态为“分流中”，不读取推荐阶段文档或提前输出其正式产物。选项可包含继续当前阶段或暂不继续，不机械罗列七阶段。

交接按剩余缺口推荐下一阶段，等待尚缺的阶段选择或决定；推荐下一阶段不等于已经进入。用户仅要当前产物时完成后停止，仍说明当前阶段与停止点。

### 业务需求与技术契约的边界

阶段三确定使用者、业务规则、权限和数据范围、兼容承诺及验收结果；阶段四确定实现它们的接口、数据结构、组件职责和故障处理。只有技术选择待定时留在阶段四；业务意图不清或必须改变时才回退阶段三。仅缺实施授权时准备检查点，不回退澄清已确定需求。

出现上游错误时回到拥有该决定的阶段：目标或方向变更按一／二／三分流，契约问题回四，任务边界或依赖问题回五。证据唯一确定去向且没有新的用户取舍时，说明依据后直接回退；否则先提供选择。回退不扩大写入授权。

### 直接进入阶段六

目标、范围、非目标、业务与数据边界、验收均明确；改动局部且可逆；无需新的行为或技术契约，独立计划也不增加执行清晰度时，可省略独立需求、Spec 和计划文件。

这条路径仍需只读反馈、阶段选择和实施授权。对于不超过三个手写文件、只改变明确的展示文案等微小变更，可在同一检查点列明推荐路径、变更范围及本地验证，允许用户一次确认。不包含生成物、锁文件、迁移、部署配置，或业务、权限、数据、安全、兼容、公共契约变化。更大但仍符合直接实施条件的任务使用普通检查点。

### 阶段六到七自动衔接

实施、自检与适用评审完成后，自动读取阶段七并验收，不再请求阶段选择。确实依赖新增授权或外部条件而受阻时，也交给阶段七记录阻塞与已有结果；仍可完成的授权内工作继续推进。

衔接不扩大验证权限。用户明确要求实施后停止时，说明阶段七尚未进行；仅禁止某一验证动作时，仍完成其余可做的验收并保留未验证项。

## 阶段外分析与诊断

用户只要解释现状、定位原因、审查或状态报告，且不要求开发阶段产物时，直接进入本出口。完成证据支持的回答即可，无需强行选择开发阶段。

“先分析再设计解决方案”通常交付阶段二成果；“只分析为什么出错，不要方案或修改”属于本出口。建议检查日志等诊断动作不自动变成方案设计。按实际交付目标判断，不把所有建议都归入阶段二。

默认只读。需要动态复现时，先读取[动作与授权](references/action-boundaries.md)，核对命令、目标及副作用的覆盖；动态诊断本身不进入实施或开发验收。报告证据、结论、未证明内容，以及已运行动作和遗留状态。

结尾明确“阶段外分析与诊断”，使用“分析完成／无需变更／阻塞／建议进入后续阶段”。发现应开发的改动时，点名建议阶段及原因；用户本轮只要诊断时可以止于建议，不自行修复。

## 共同边界与按需细则

### 实施与验证

在准备实施检查点、首次实施或运行可能产生副作用的验证前，读取[动作与授权](references/action-boundaries.md)。其中统一定义授权范围、验证副作用和评审条件；阶段文档不另立授权规则。

用户决定业务和有实质影响的取舍；能够通过安全只读调查确定的事实自行查明。只询问会改变结果、范围、权限、数据、兼容、成本或验收的缺口。不改变这些事项、位于既定范围内的可逆内部细节可自主决定。

阶段选择、产物确认、文档写入、实施与验证、Git 和外部变更分别判断，可以合并请求，但不能相互推导。确认不足时说明缺少哪个决定；因为技能约定暂停时，链接本文件并引用实际适用的条款，不把解释当成宿主限制。

### 正式产物与修订

阶段三至五写正式产物前，或修订已被下游采用的依据时，读取[产物与追溯](references/artifact-contracts.md)。固定产物名为 `requirements.md`、`spec.md`、`implementation-plan.md`；优先遵循项目文档位置，否则放在 `.product-development-workflow/<task-slug>/`。

阶段三的正式需求文件需要文档授权；阶段四、五在内容、状态和路径确定时直接保存正式文件，无需单独申请 Markdown 权限。保留任务身份、已有内容、可恢复修订和写后回读；文档产出不授权代码实施。

沿用稳定的需求标识；需要建立映射且输入未编号时，在当前产物或对话补齐 `R-*` 与来源。不要因此补造上游文件或重新确认既定需求。依据修订后分别核对下游文档、实施、评审和验证的有效性。

## 每轮交付与结尾

开头简要说明当前阶段及选择依据；分流未完成时说明推荐而非已进入。正文直接交付本轮需要的结果，按任务复杂度控制长度；未知项不补成决定，正式文件保存后给摘要与可点击路径。

**每次面向用户的最终回复都以可识别的阶段交接收尾**，用短段落即可，无需固定大模板。包含：

1. **当前位置**：阶段编号与名称，或“分流中／阶段外分析与诊断”。
2. **本轮状态**：已完成的产物、待确认决定或阻塞；涉及实施时同时说明授权与验证状态。
3. **下一步**：点名建议阶段及理由、继续当前阶段的具体事项，或“本轮到此结束”。尚待选择时给出合理选项；已授权的下一步应继续完成，不把它留成让用户重复授权的建议。

例如，方案输出可收尾为：“当前为阶段二：方案头脑风暴，推荐方向待你选择。采纳后建议进入阶段三，明确支持入口和参数有效期；也可留在阶段二比较备选，或保留方案暂不继续。”不能仅以“分析完成、未修改文件”替代阶段交接，也不能把推荐写成已进入阶段三。

阶段七只有“已通过开发验收”可以声明开发交付完成；其他状态说明具体剩余条件。开发验收不代表已提交、部署或生产验证。
