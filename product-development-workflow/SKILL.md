# 产品开发工作流

## 目标

用一个入口处理从模糊想法到有证据支持的开发交付。先判断当前最早的关键未知项，再只进入一个阶段；不要把机会假设、候选方案、已确认需求、技术规格、实施计划、完成证据和执行授权混为一谈。需求描述本身永远不是阶段六实施授权；阶段四、五正式产物按本工作流的持久化规则直接写入 Markdown。

本目录只有本文件是对外入口。`references/` 下的七个文档是内部阶段能力，不作为独立 Skill 安装或调用。每次只读取当前阶段文档；本工作流不依赖外部 Skill 才能完成阶段五至七。

## 七阶段与分流

| 用于生成选项的分流判据 | 进入阶段 | 读取的内部文档 | 本阶段产物 |
| --- | --- | --- | --- |
| 是否存在值得解决的用户问题或机会 | 阶段一：产品需求探索 | references/product-discovery.md | 证据、机会假设和最小验证计划 |
| 已确认问题，但产品形态、流程或技术方向未知 | 阶段二：方案头脑风暴 | references/brainstorming.md | 有取舍的候选方案和用户选择 |
| 已选问题与方向，但业务规则、权限、数据边界、范围或验收未知 | 阶段三：开发需求澄清 | references/clarifying-development-requirements.md | 可执行、可验收的开发需求及授权边界 |
| 需求已确认，但系统行为、技术职责、数据或接口契约、异常、兼容或验证策略未知 | 阶段四：编写开发规格 | references/writing-specs.md | 经审阅的技术与行为规格说明 |
| 需求或 Spec 已确认，但文件级改动、任务依赖、测试步骤或执行方式未知 | 阶段五：编写实施计划 | references/writing-implementation-plans.md | 可执行、可追溯且经自检的文件级计划 |
| 计划已就绪且已授权修改工作区，但代码、测试或文档尚未完成 | 阶段六：执行开发计划 | references/executing-development-plans.md | 已实施并经过任务级自检与适用评审的变更 |
| 实施已结束，但尚无新鲜证据证明符合需求、质量要求和验收标准 | 阶段七：验证与验收 | references/verification-and-acceptance.md | 带证据的完成结论、遗留项和验收交接 |
| 目标、范围和验收均清晰，修改局部、可逆、低风险，且已取得符合下述规则的工作区修改授权 | 取得独立授权后直接进入阶段六 | references/executing-development-plans.md；完成后读取阶段七文档 | 说明授权依据和范围后实施并验证 |

若多个未知项同时存在，从最早且最影响方向的一项开始。发现先前假设不成立、问题并未确认或用户改变目标时，回退到适用的前一阶段。

### 阶段选择由用户确认

上表用于形成推荐，不授权 AI 静默进入阶段。首次分流或准备从一个阶段转入另一个阶段时，先做必要的安全只读调查，再向用户提供 2 至 3 个互斥选项：

- 将拟进入的阶段放在第一项并标记为 `（推荐）`，用一句话说明推荐依据和选择后的产物；
- 只列真正合理的相邻阶段、留在当前阶段或暂不继续等备选，不为凑数列出全部七个阶段；
- 宿主支持结构化选项时优先使用；否则使用简短编号选项。用户仍可明确指定未列出的阶段。

用户选择前，只能继续支持分流所需的安全只读调查；不得声称已进入推荐阶段，不得读取该阶段内部文档、输出该阶段正式产物或修改工作区及外部状态。

若用户已明确指定阶段、明确要求该阶段的产物或确认了上一阶段的交接建议，则视为完成阶段选择，不重复询问。初始需求中的“修改”“修复”“实现”“帮我处理”等措辞不视为阶段六选择，也不构成阶段六实施授权；用户明确指定阶段六时，只完成阶段选择，仍须单独取得覆盖实施范围的工作区修改授权。

### 阶段六实施授权必须来自后续回复

阶段四、五正式 Markdown 产物按下述持久化规则直接写入。除这一有限例外外，用户首次提出任务时，无论使用陈述句、祈使句，还是“直接修改”“帮我修复”“立即实现”等措辞，都只是在描述期望结果，不授权 AI 修改生产代码、测试或其他实施文件。不得根据语气、动词、任务清晰度、低风险判断、宿主模式、已有文件访问权限或历史合作习惯推断阶段六实施授权。

建立阶段六工作区修改授权必须依次发生：

1. AI 先完成必要的安全只读调查，向用户反馈当前理解、拟修改范围、非目标和验证方式；
2. AI 明确进入授权检查点，并针对已经说明的范围询问是否允许修改工作区和执行本地验证；
3. 用户在后续消息中以 `确认`、`开始执行`、`按此修改`、`同意实施` 等肯定命令回复，授权才成立。

肯定回复只确认 AI 上一条消息明确请求的事项。如果上一条消息只询问需求、Spec、计划或阶段是否正确，用户回复 `确认` 只确认对应产物，不构成阶段六实施授权；阶段四、五产物随后按专门规则直接持久化。授权只覆盖检查点列明的范围和操作；新增范围、Git 历史操作、远程写入、发布、部署或生产验证仍需各自的后续授权。

阶段四、五自动写入 `spec.md` 或 `implementation-plan.md` 不构成阶段六实施授权。取得阶段六授权后，在首次实施写入前先向用户说明当前阶段、授权依据和本次修改范围。若无法指出对应的授权检查点及用户后续肯定回复，不得修改生产代码、测试或其他实施文件。

## 统一工作规则

1. 先区分用户陈述、已观察证据、推断、机会假设、候选方案、用户决定、已确认需求、规格技术决定、计划技术决定、实施结果、验证证据和执行授权。
2. 先做必要的安全只读调查；不要把代码、日志、现有实现或常见做法写成未来业务意图。
3. 每轮优先处理一个会实质改变结果的决策主题。能从资料或只读检查确定的事实，不转嫁给用户。
4. 在每个阶段结束时明确列出仍未知的事项、所需用户决定和下一阶段选项；未经用户选择不得静默跳阶段。
5. 将需求确认、Spec 确认、计划确认、阶段六实施授权、仓库操作授权和外部状态变更授权分别处理。阶段四、五文档按专门规则自动持久化；选定问题、方案、技术设计或计划仍不等于允许实施，只有授权检查点后的用户肯定回复才能建立阶段六实施授权；完成开发也不等于允许提交、合并、推送或部署。

## 执行方式

1. 用上表形成阶段推荐，按“阶段选择由用户确认”取得选择后，再只读取已选阶段对应的内部文档。
2. 完整遵循该阶段文档中的调查、提问、输出和安全要求；不要同时加载或混用其余阶段的详细流程。
3. 达到阶段交接门槛后，向用户说明仍需的决定或授权，并提供下一阶段选项；取得选择后才能进入下一阶段。
4. 清晰、局部、可逆且不需要新增契约或文件级计划的工作，可以跳过独立计划；但只有在完成授权检查点并收到用户后续肯定回复后才能进入阶段六。任何实施路径都必须进入阶段七，才能声称完成。
5. 阶段六发现计划错误时回到阶段五；发现 Spec 错误时回到阶段四；发现业务意图或边界错误时回到阶段三或更早阶段。不得在代码中静默改变上游决定。

## 阶段交接门槛

- 阶段一到阶段二：用户已确认要解决的问题或明确接受在指定风险下继续；验证不足时留在阶段一。
- 阶段二到阶段三：用户已选择方向，或明确接受带影响说明的推荐方向；方案仍只是候选时不得伪装成需求。
- 阶段三到阶段四：目标、关键业务与数据边界、范围、非目标和验收标准已经确认；阶段四只细化技术与行为契约，不重新决定业务意图。
- 阶段三到阶段五：需求已确认且不需要新增技术或行为契约，但工作涉及多个任务、文件、依赖或检查点，独立计划能降低实施风险。
- 阶段四到阶段五：Spec 已审阅、没有实质未决项，并允许起草计划；阶段五正式产物的内容、状态和路径确定后按下述持久化规则直接保存，不另行申请 Markdown 写入权限。
- 阶段五到阶段六：计划已覆盖需求与适用的 Spec、任务依赖和验证方式，没有会改变用户可见结果的未决项，并已通过授权检查点和用户后续肯定回复取得覆盖阶段六实施范围的工作区修改授权。
- 阶段六到阶段七：计划内任务已经实施并完成任务级自检与适用评审；或者未完成项已有可复查的阻塞证据，且必须依赖新授权或外部条件才能继续，以便阶段七形成阻塞报告。此时仍不得声称整体完成。
- 阶段七形成结论：基于新鲜证据输出 `已通过开发验收`、`待用户验收`、`条件通过`、`未通过` 或 `阻塞`，并如实披露失败、遗留项和剩余条件。
- 阶段七到已完成开发交付：只有状态为 `已通过开发验收` 时成立；其余状态只能结束本轮验证、请求验收或回到相应阶段，不能声称开发交付完成。
- 直接进入阶段六：目标、关键业务与数据边界及验收标准均已明确，修改局部、可逆，不需要新增技术或行为契约及独立实施计划；AI 已反馈范围和验证方式并进入授权检查点，用户随后作出肯定回复。低风险内部细节可由项目规范决定，但仍须进入阶段七。

## 阶段三至五的持久化产物

阶段三至五把过程讨论与正式交接产物分开：

- 澄清、候选选择、草稿审阅和未决项处理在对话中进行，不为每轮交流创建新文件。
- 当阶段三至五已经具备形成完整正式产物的条件时，必须在输出完整正文前先确定目标文件：阶段三为 `requirements.md`，阶段四为 `spec.md`，阶段五为 `implementation-plan.md`。阶段三若满足直接进入阶段六的条件，可以省略独立需求文件。
- 文件位置优先遵循项目规范或现有文档布局；没有适用约定时，使用 `docs/development/<task-slug>/` 目录，并在同一任务目录中维护上述三个稳定文件名。更新同一阶段产物，不为每次修订创建重复版本。
- 阶段三形成完整 `requirements.md` 时，必须先说明具体文件路径、拟记录内容、非目标和验证方式，进入仅针对该文档的工作区修改授权检查点。尚未取得文档写入授权时，停止在检查点并请求授权；收到用户后续肯定回复后再创建或更新文件。路径、产物类型或范围变化时重新确认。
- 阶段四 Spec 或阶段五实施计划的内容、状态和目标路径已经确定，且不存在会改变正式产物的实质未决项时，必须直接创建或更新对应的 `spec.md` 或 `implementation-plan.md`，不得再为这些文件申请单独写入权限。首次写入前说明当前阶段、目标路径和即将持久化的产物即可，不等待用户再次确认。
- 阶段四、五的直接写入只覆盖对应的正式 Markdown 产物，不授权 `requirements.md`、生产代码、测试、Git 历史、部署或外部状态变更。目标路径、产物类型或覆盖范围尚未确定时，先解决该未决项，不得用写入授权请求代替内容或路径确认。
- 文件写入后，对话只输出结论摘要、可点击的文档位置、产物状态、关键决定、未决项、未覆盖范围和后续路径，不重复粘贴完整正文。只有用户明确要求仅在对话中产出、明确拒绝文档写入、没有可写工作区，或任务明确止于分析或非正式草稿时，才在对话中输出完整 Markdown 产物。

## 输出要求

阶段尚未确认时，先说明推荐阶段和依据并提供选项；阶段已经确认时，先说明当前所处阶段和依据。随后仅输出已确认阶段要求的产物，并清楚标示证据来源、假设、用户决定、未覆盖范围和所需授权。阶段三至五遵循上述持久化产物规则：阶段三按需请求 `requirements.md` 写入授权，阶段四、五在产物确定后直接写入对应 Markdown。请求阶段六工作区修改授权时，明确说明尚未实施；取得授权后，在首次实施写入前说明授权依据及其覆盖范围。

若用户只要求分析、探索、需求、Spec 或计划，止于相应阶段的产物；除阶段四、五按规则直接持久化的正式 Markdown 外，不修改其他工作区文件、仓库或外部系统。阶段七只判定开发交付；提交、合并、推送、发布、部署和生产验证仍需单独授权及适用流程。

## 快速检查

- 当前是在确认要解决什么、比较怎么做、澄清交付边界、定义契约、编写计划、实施，还是验证验收？
- 当前结论是机会假设、候选方案、开发需求、Spec、实施计划、实施结果，还是有证据的完成结论？
- 是否把事实、推断、用户决定、技术决定、实施结果和验证证据分开？
- 是否从最早的关键未知项开始，而不是直接假定方案、需求或技术设计？
- 除阶段四、五已确定的正式 Markdown 产物外，阶段六工作区修改授权是否来自授权检查点后的用户肯定回复，而不是从初始需求措辞中推断？
- 是否在进入实施和外部变更前分别获得了与风险相称的确认和授权？
- 是否只在读取新鲜验证证据后声称完成？
