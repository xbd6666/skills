# skills

> 一组可复用、可移植的 AI 助手 Skills，帮助代理在重复任务中遵循稳定的工作流、边界与验证要求。

本仓库的核心是每个 Skill 目录中的 `SKILL.md`。它描述任务何时触发、应如何执行以及需要遵守的约束，不绑定某一个 AI 产品或代码代理。不同宿主对 Skill 的发现、安装和调用方式可能不同；请按宿主的机制导入目录，并保留目录内的相对结构。

## 适用场景

- 希望把个人或团队反复使用的 AI 工作流沉淀为可复用资产。
- 希望 AI 在操作数据库、澄清需求或修改代码前遵循明确的安全边界。
- 希望为不同类型的仓库建立可追溯、可维护的工程约定。
- 希望避免每次对话都重复说明流程、风险与验收要求。

## 内置 Skills

| Skill | 解决的问题 | 典型触发 | 关键约束 |
| --- | --- | --- | --- |
| [`project-conventions`](./project-conventions/SKILL.md) | 检查、规划、创建或更新项目规范文档 | 需要 `CONVENTIONS.md`、`AGENTS.md`，或要梳理目录职责和架构边界 | 使用`检查现有约定 / 制定约定方案 / 创建或更新约定`；默认制定方案；先识别既有权威，验证权限与文档写入分开 |
| [`dbx-mcp`](./dbx-mcp/SKILL.md) | 通过 DBX MCP 安全地检查和操作数据库 | 查看连接、检查 schema、编写/执行 SQL、导入结构化数据 | 先发现连接与 schema；高风险写操作须有明确确认；写后复查 |
| [`product-development-workflow`](./product-development-workflow/SKILL.md) | 从问题发现到有证据支持的开发交付 | 产品或开发请求的问题、方案、交付边界、技术契约、实施计划或完成状态尚不明确 | 一个公开入口按阶段分流；保留证据、用户决策、追溯关系与执行授权边界 |

## 快速开始

### 1. 获取仓库

```bash
git clone https://github.com/xbd6666/skills.git
```

也可以只获取所需的单个 Skill 目录。

### 2. 导入到你的 AI 助手

将目标 Skill 的完整目录导入或复制到宿主所识别的 Skills 位置。例如，使用 `project-conventions` 时，应一并保留：

```text
project-conventions/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── request-contract.md
│   ├── discovery.md
│   ├── inheritance.md
│   └── verification.md
├── assets/
│   ├── 检查现有约定报告.template.md
│   ├── 制定约定方案.template.md
│   ├── 根级.CONVENTIONS.template.md
│   ├── 模块.CONVENTIONS.template.md
│   ├── 根级.AGENTS.template.md
│   └── 模块.AGENTS.template.md
└── tests/
    ├── README.md
    └── behavior-cases.json
```

- `SKILL.md` 是必需的通用指令入口。
- `references/` 保存按工作方式和场景读取的详细规则，`assets/` 保存输出模板；使用时应保留两者的相对结构，不能只复制 `SKILL.md`。
- `agents/openai.yaml` 是可选的界面元数据；不识别它的宿主可以忽略，不影响 `SKILL.md` 的核心工作流。
- `tests/` 保存本技能维护用的行为场景和回归方法，常规约定任务不需要加载。

> 以下示例使用 `$skill-name` 形式调用。若你的宿主采用其他调用语法，请按其文档替换触发方式。

### 3. 调用 Skill

```text
使用 $project-conventions 为当前项目制定有证据支持的 CONVENTIONS.md 与 AGENTS.md 方案；本轮不要写入文件。

Use $dbx-mcp to inspect my DBX connections and help write a safe SQL query.

使用 $product-development-workflow 将这个产品或开发想法分流到探索、方案、需求澄清、规格、实施计划、开发执行或验证验收阶段。
```

#### product-development-workflow：按当前状态调用

不需要预先判断自己处于哪个阶段。说明已知事实、当前不确定项和希望做出的决定即可；Skill 会从最早的关键未知项开始。

**阶段外只读：只需要分析、诊断或状态报告**

```text
使用 $product-development-workflow 只读分析当前开发流程的一致性和逻辑漏洞。
不要修改文件、运行会生成产物的命令或进入七阶段；如果现状已经满足目标，请以“无需变更”结束。
```

**阶段外动态诊断：需要复现，但暂不修复**

```text
使用 $product-development-workflow 诊断导出失败的原因，暂不修复。先检查已有日志与代码；如果必须运行测试或启动本地服务，说明要验证的假设、命令、目标、副作用及临时产物范围，复查对应授权，缺少覆盖时先请求授权。复现后报告证据和未证明的内容，不把复现成功当成已修复或已验收。
```

**1. 产品需求探索：问题或价值尚未确认**

```text
使用 $product-development-workflow 帮我判断是否值得为诊所前台做“患者到诊提醒”。
目前只有同事的零散反馈，还不清楚哪些岗位最受影响、现有做法的代价，以及应先验证什么；请先不要设计功能或修改文件。
```

**2. 方案头脑风暴：问题已确认，但不知道怎么做**

```text
使用 $product-development-workflow 设计解决方案。
我们已确认销售在跟进客户时很难找到历史沟通记录；请比较复用现有 CRM 搜索、增加客户时间线和引入 AI 摘要三种方向，并说明各自价值、成本、风险和最小验证方式。
```

**3. 开发需求澄清：方向已选，但交付边界不完整**

```text
使用 $product-development-workflow 澄清需求。
我们决定在现有后台增加“聊天记录导出”功能，但尚未确定谁可以导出、数据范围、脱敏规则、失败提示和验收标准。请先只读检查现有权限与筛选逻辑，再逐项确认会改变用户可见结果、权限、数据或验收结论的事项；暂不修改文件。
```

**4. 编写开发规格：需求已确认，但技术与行为契约尚未明确**

```text
使用 $product-development-workflow 编写规格。
聊天记录导出的用户、权限、范围、脱敏规则和验收标准已经确认；请只读检查现有导出、权限和接口模式，定义组件职责、数据与接口契约、失败语义和验证策略。先产出供阶段五使用的 Spec，不修改代码或创建提交。
```

**5. 编写实施计划：Spec 已确认，但文件级任务尚未确定**

```text
使用 $product-development-workflow 编写实施计划。
聊天记录导出 Spec 已确认；请调查相关文件和测试，建立需求、Spec、任务与验证的追溯关系，形成文件级计划。只保存计划，不修改生产代码，不创建分支或提交。
```

**6. 执行开发计划：计划已就绪且已授权修改工作区**

```text
使用 $product-development-workflow 执行已确认的聊天记录导出实施计划。
允许修改计划列出的工作区文件并运行本地验证；不创建分支、不提交、不推送、不部署。发现计划、Spec 或业务规则有问题时回到对应阶段，不要在代码中自行改变。
```

**7. 验证与验收：实现结束，但尚未形成完成证据**

```text
使用 $product-development-workflow 验证聊天记录导出是否可交付。
先核对既有证据与当前状态，复用完整、可复查且仍有效的结果，只补齐缺失、受影响或无法确认有效的验证。补充执行前复查已有授权是否覆盖命令、副作用和范围，缺少时先请求相应授权。区分复用证据、新执行的定向或完整测试和预存失败，并输出需求到证据的追溯及待人工验收项。不要提交、推送或部署。
```

**微小变更快捷通道：合并检查点，但不能跳过授权和验证**

```text
使用 $product-development-workflow 处理以下清晰修改：将管理后台用户列表空状态中的“暂无数剧”改为“暂无数据”，并更新对应测试。先只读确认是否满足最多三个手写文件、无业务歧义且不改变公共契约、权限、数据或安全语义的快捷通道门槛；满足时在一条消息中分别列明阶段选择、范围/非目标/验收结果和实施/验证授权请求。收到我明确覆盖这些事项的后续肯定回复后再实施，不创建分支、不提交、不调用外部系统。
```

## project-conventions 工作方式

`project-conventions` 用于把仓库中实际存在的结构、构建方式和边界，整理为人类与 AI 代理都能遵守的项目约定。

### 三种工作方式

| 工作方式 | 行为 | 是否写入约定文档 |
| --- | --- | --- |
| `检查现有约定` | 检查现有约定、冲突、缺口和实现漂移 | 否 |
| `制定约定方案` | 输出发现报告、推荐布局、准确文件清单与变更摘要 | 否；默认工作方式 |
| `创建或更新约定` | 按已解析范围创建或最小更新约定文档 | 仅写入已解析的约定文档 |

明确要求“生成”“创建”“更新”“写入”或确认上一轮可唯一识别的约定方案时，Skill 才会执行`创建或更新约定`。对于已有文档，使用“保留、更新、替换”区分不改现有文件、最小更新和明确重写；约定文档授权不包含代码、Git、数据库、部署或外部系统操作。

验证权限与工作方式独立：默认只读发现，当前会话已授权的具体验证可以执行并单独记录产物，检查或方案仍不写入约定文档。记录命令时同时说明工作目录、前提、范围、副作用与证据状态；已有授权覆盖的动作不重复确认。报告中的工作方式和契约值按输出语言展示，文件名、路径及命令保持原文。

### 生成前的证据链

Skill 会先记录用户已明确的契约字段，把需要仓库证据才能判断的值标为“待发现”；完成发现后再最终解析范围、布局和语言。单点检查只读取目标、适用指令和直接证据，遇到相关冲突或依赖再扩大范围，可以简短交付；完整方案与多规则维护记录：

1. 请求的工作方式、范围、布局、语言和已有文档处理策略。
2. 从仓库根到目标目录的 `CONVENTIONS.md` 与 `AGENTS.md`。
3. 每项证据的类型、观察事实、反例或冲突、结论状态、规则影响和置信度。
4. 无法从仓库确认的假设与待确认事项。

因此，单个实现样本、历史例外或未从仓库证实的框架、验证命令、职责边界与依赖方向不会被伪装为既定事实；文档与实现不一致时先报告漂移，不自行判定哪一方错误。

只有已确认规则可以写为生效条款。重复惯例形成的候选，需要用户明确采纳具体内容及适用范围；可随方案中的明确清单批量确认，一般写入授权不等于采纳候选。未采纳内容只列为不生效的待确认事项，不阻塞与其独立的已确认规则交付。

### 规范文档的继承

先识别既有权威关系，专业工程文档及既有 AGENTS 的有效主题权威可以继续保留；使用 Skill 或创建缺失文档不等于迁移授权。需要迁移时明确主题、原权威、目标文档和原内容处理方式。以下是新建体系或已采用该分工范围内的默认继承规则：

- 父级 `CONVENTIONS.md` 默认适用于子目录。
- 子模块新增局部规则属于扩展，与父级规则叠加，不免除父级同一主题的要求；改变父级规则时，在子级 `CONVENTIONS.md` 的“覆盖项”中记录上级文档、主题、被改变的规则部分、理由和适用边界，其余父级要求继续适用。
- 上级仅重命名时更新引用并保留覆盖语义；规则内容或范围变化时重新判断覆盖，实际删除时先查明是否迁移或被其他规则承接，不自动改成扩展或删除。
- 父规则变更前后检查受影响的子级文档和规则引用，包含未显式引用但受继承影响的文档；必要联动修改超出已授权范围时，先报告准确文件和影响，确认范围后再应用关联变更。
- `AGENTS.md` 保留规则路由、有来源的职责与高风险执行提醒，验证入口引用权威来源；不借模板建立长期政策，也不把一次性任务限制持久化为仓库规则。
- 更局部的 `AGENTS.md` 可以依据已确认权威来源增加或收紧护栏，不能放宽父级限制；无法同时满足的冲突会阻止受影响写入并交给用户裁决。

常见产物：

- `CONVENTIONS.md`：面向团队的长期工程约定。
- `AGENTS.md`：面向代理的短入口说明。
- 现有约定检查报告：按严重度给出问题、证据、影响和建议，不包含写入计划。
- 约定方案：给出推荐布局、准确文件清单、规则来源和可唯一确认的创建或更新范围。

维护本技能时可按[行为场景回归说明](./project-conventions/tests/README.md)选择相关场景；结构检查和静态推演不等同于实际模型行为重放。

## dbx-mcp 工作方式

`dbx-mcp` 适用于已提供 DBX MCP 能力的宿主。它不保存任何项目的账号、密码或连接信息，而是要求代理按以下顺序工作：

1. 查找或建立连接。
2. 检查表、视图和 schema。
3. 使用限定条件执行读取查询。
4. 对写入、删除、DDL 或大范围更新先进行风险确认。
5. 写入后重新查询受影响记录、计数或完整性条件。

如果 DBX MCP 不可用，Skill 会要求先发现相应能力，而不是凭空假设数据库连接或凭据。

## product-development-workflow 工作方式

该 Skill 对外只有一个入口，内部按当前最早的关键未知项进入七个阶段：

明确只要求分析、诊断、审查、解释、状态检查或报告的请求，走七阶段之外的[分析与诊断出口](./product-development-workflow/SKILL.md#阶段外分析与诊断)，默认安全只读。静态证据不足时，可以在覆盖具体动作及副作用的授权内动态复现，仍不进入开发实施或验收；可结束为“分析完成”“无需变更”“阻塞”或“建议进入后续阶段”。

1. **产品需求探索**：确认用户、场景、痛点和价值机会，并形成可验证的假设。
2. **方案头脑风暴**：针对已确认的问题，生成、比较并收敛不同的产品、流程或技术方向。
3. **开发需求澄清**：将已选方向整理为带范围、业务规则、验收标准和授权边界的可执行需求。
4. **编写开发规格**：将已确认需求转为经审阅的技术与行为 Spec。
5. **编写实施计划**：把已确认需求和适用的 Spec 转为带文件职责、任务依赖、验证方式和追溯关系的可执行计划。
6. **执行开发计划**：在授权范围内实施任务，完成任务级自检和适用评审；发现上游错误时回退到正确阶段。
7. **验证与验收**：用当前证据验证需求、Spec、质量和验收标准，形成明确的开发交付结论。

阶段三与四按[业务需求和技术契约](./product-development-workflow/SKILL.md#业务需求与技术契约的边界)区分：技术契约待定留在规格阶段，只有业务意图需重新决定时才回退。正式产物记录修订及采用的上游依据，覆盖已确认或已被采用的旧版前确保其内容可取回；修订后按[下游有效性规则](./product-development-workflow/SKILL.md#产物修订与下游有效性)分别复核文档、任务、评审和验证，文档恢复有效不等待下游实施。阶段六写入前保留相关改动基线，并分别采用正常交接或阻塞交接，避免遗漏用户已有改动或把未完成评审伪装成通过。

阶段文档只在需要时读取，避免把探索、决策、计划、实施结果和完成证据混成同一份结论。满足入口[“直接进入阶段六”](./product-development-workflow/SKILL.md#直接进入阶段六)门槛的修改不强制新增上游产物，但必须取得工作区修改与本地验证授权。阶段六满足正常或阻塞交接门槛后[自动衔接阶段七](./product-development-workflow/SKILL.md#阶段六到七自动衔接)，无需再次选择阶段，也不增加动作授权；用户明确要求暂不验收时停止，只有通过阶段七验收才能声称开发交付完成。

需求追溯标识由首次建立映射的阶段沿用或补齐，并关联原始需求与验收标准，不因缺编号强制补做上游阶段。阶段七先按[证据复用条件](./product-development-workflow/references/verification-and-acceptance.md#既有验证证据的复用)核对已有结果，复用仍有效的部分，只补齐缺失或受影响验证。验证动作命中多个副作用类别时，须同时满足全部适用授权。

阶段按尚缺的信息选择；仅缺实施授权时准备对应检查点，不因此回到需求澄清。相邻检查点可以在一轮中分别确认，例如同时确认 Spec 并进入阶段五，或在计划、范围、非目标和验证方式已经完整说明后，同时确认计划并授权实施。每项确认必须明确编号或能够被用户回复唯一指向；含糊的“确认”不能扩大实施、Git 或外部状态授权。

预计不超过三个手写文件、目标与验收明确、改动可逆，且不改变公共契约、业务规则、权限、数据、安全或兼容语义的微小变更，可以把阶段选择、变更契约和阶段六授权合并到一次编号检查点。首次请求仍不是实施授权；任一门槛失效时立即退出快捷通道并按普通分流处理。

阶段五至七借鉴了 Superpowers 的实施计划、任务级执行与评审、完成前验证思想，并按本仓库的可移植性和授权边界重新设计；不要求安装 Superpowers，也不默认创建 worktree、分支、提交、推送或部署。参考：[obra/superpowers](https://github.com/obra/superpowers)。

## 兼容性与边界

- 核心指令以 `SKILL.md` 提供，目标是可迁移到支持 Skills 或等价指令机制的 AI 助手。
- 仓库中存在的 `agents/openai.yaml` 仅是某类宿主可使用的可选界面元数据，不是使用 Skill 的前置依赖。
- 不同宿主的安装位置、自动发现机制、工具命名与调用语法可能不同；导入前请查阅对应宿主的说明。
- `dbx-mcp` 依赖 DBX MCP 及相应数据库访问权限；其余 Skills 不要求特定外部服务。
